## 1. 项目概述

SHANIU 是一款 **Windows 桌面 Agent Harness 客户端**：在本地托管自主编码 Agent 的完整生命周期——任务输入、模型推理循环、工具执行、沙箱隔离、人工审批、流式渲染与会话持久化。

| 项 | 值 |
| --- | --- |
| 技术栈 | Tauri 2.12.5 + React 19.3.1 + Rust 1.99.1 + Vite 8.3.5 |
| 目标平台 | Windows 10/11 x64（**仅此平台**；不承诺 Linux/macOS，非 Windows 目标在编译期失败，见 `docs/10` §4） |
| 进程模型 | 单进程：Tauri Rust 后端承载全部 Agent 逻辑，WebView 前端通过 IPC 通信 |
| 开发方式 | 全部代码由 AI 编码代理产出，受 `AGENTS.md` 约束 |

### 1.1 目标（Goals）

- G1：提供完整的自主编码循环——用户下达任务后，Agent 自主规划、读写文件、执行命令、自我纠错，直到任务完成或被中断。
- G2：**真实沙箱**，不是"仅提示"——Windows 上通过受限令牌（Restricted Token）+ Job Object + ACL 实施文件系统边界（网络不是策略维度，2026-11-10 起命令一律可出网）；策略无法满足时拒绝执行（fail-closed）。
- G3：风险分级审批——只读工具自由执行，写入/命令按沙箱策略与审批模式裁决，破坏性操作必须人工确认。
- G4：流式体验——模型输出、命令输出、diff 全部流式渲染，支持随时中断（CancellationToken）。
- G5：会话可恢复——rollout 持久化（JSONL），支持 fork/resume/replay。

### 1.2 非目标（Non-Goals）

- 不做多用户/协作/云端同步（单机单用户）。
- 不做自有模型推理，仅对接兼容 OpenAI Responses/Chat Completions 协议的远端或本地端点。
- 首版不做 MCP 市场/插件 UI 沙箱（保留协议扩展点，见 ADR-004）。
- 不打包子 Agent 并行编排（`multi_agents` 列入二期候选）。

### 2.2 有界上下文图（Bounded Context Map）

| Context | 职责 | 模型/语言 | 上游 | 下游 | 与邻接关系 | 翻译面 |
| --- | --- | --- | --- | --- | --- | --- |
| `ui`（前端） | 渲染会话流、审批交互、配置 | TypeScript/React | `events` | 用户 | conformist（完全消费后端事件模型） | `EventMsg`→视图节点（conversation-nodes 模式） |
| `agent_loop` | turn 循环：Sampling→ToolCall→回填 | Rust | `model_client`、`tool_router` | `events`、`rollout`、`compaction` | partnership | 模型协议 item → 内部 `ResponseItem` |
| `tool_router` | ToolSpec 注册/路由/参数校验 | Rust | `agent_loop` | `tools/*` | shared kernel（ToolSpec 是共享契约） | JSON Schema ↔ Rust 参数类型 |
| `tools/*` | 具体工具执行（exec/patch/plan/fs） | Rust | `tool_router` | `permission`、`sandbox` | customer/supplier | 工具入参 → OS 调用 |
| `permission` | 审批模式、风险分级、裁决 | Rust | `tools/*` | `ui`（审批请求） | partnership | 工具风险等级 → 审批事件 |
| `sandbox` | 进程隔离原语（Windows） | Rust + Win32 | `tools/unified_exec` | OS | anti-corruption layer | 沙箱策略 → RestrictedToken/JobObject/ACE |
| `model_client` | LLM HTTP 流式客户端 | Rust | `agent_loop` | 远端 API | anti-corruption layer | Responses SSE → `ResponseItem` 流 |
| `rollout` | 会话持久化/fork/resume | Rust | `agent_loop` | 磁盘 | separate ways | `RolloutItem` ↔ JSONL |
| `compaction` | token 预算判定 + 历史摘要压缩 | Rust | `agent_loop` | `rollout`（写 `Compacted` 锚点） | separate ways | 历史区间 → `Compacted{range, summary}` |
| `events` | 事件协议定义+广播 | Rust | 全部 | `ui` | shared kernel | `EventMsg` → Tauri Event 序列化 |

### 2.3 依赖方向规则（不可违反）

`ui → events`；`agent_loop → {model_client, tool_router, rollout, events}`；`tool_router → tools/*`；`tools/* → {permission, sandbox}`；**禁止反向依赖，禁止 `tools/*` 直接访问 `model_client` 或 `ui`**。

> 上述一行是规则摘要；**完整清单以下面 2.3.1 的允许边表为准**——摘要表漏登的边若出现在 2.3.1，即视为合法（例如 `agent_loop → permission`、`tool_router → model_client`）。

#### 2.3.1 允许的边（全量清单）

> **本表是 FF-1（依赖方向不变量：违规数 = 0）的唯一事实来源**：规则变更必须先改本节、再改脚本，禁止反过来——先改脚本等于把架构规则藏进脚本，评审看不见，必然与本文档漂移。
> **现状（实然）**：`scripts/check-deps.ps1` 按本表**正向校验**（白名单 + fail-closed）：表外模块判违规并提示先在本节登记；`config`/`events` 为共享基础设施、任何模块可依赖且自身只依赖二者；`lib.rs`/`main.rs`/`app_state.rs` 为组合根，跳过判定。
> **为什么用白名单**（SH-076，已随 SH-009 落地 2026-11-05）：黑名单的失效模式是**静默豁免**——新模块天然落在规则之外，坏边一条不报而 CI 照样绿；多报一条能被看见，漏报一条没人知道。

| E48 | `agent_loop` → `sandbox` | 系统提示每轮重算需要宿主 OS 模式（`current_os_mode`）；这是**只读策略查询**，执行入口仍只在 `tools → sandbox`（E13）。网络不是策略维度（2026-11-10），提示词不再查询任何网络状态 |
| E49 | `sandbox` → `text_encoding` | 子进程输出必须按实际编码解码（UTF-8/GBK 自动判别）；`text_encoding` 是零 crate 内依赖的叶子 |
| E50 | `tools` → `text_encoding` | 同 E49：`unified_exec` 直接消费解码结果，不再各自维护第二份猜测逻辑 |
| E51 | `model_discovery` → `capability` | 端点元数据只有一套防御性解析（`parse_metadata`）：两种字段形状、类型不符按缺失；第二份必然与探针漂移（与 E08/E21 同源理由） |
| E52 | `model_client` → `images` | 会话条目 `ImageMessage` 持久化 `ImageRef`，请求构造时按 sha256 从 `image_store` 取字节；字节永不进档案 |
| E53 | `tool_router` → `images` | 共享内核承载 `ImageBudget` 与 `attachment()`（读回 `ImageRef`），避免 `agent_loop → tools` 越层（§2.3.2） |
| E54 | `tools` → `images` | `view_image` 存字节并构造引用；经 `images` 而不是 `model_client`——后者是 §2.3.2 明令禁止的边 |
| E55 | `capability` → `app_state` | SH-132 能力探针的命令壳经 `app.state::<AppState>()` 取数据根与 DPAPI 密钥；`config`/`events` 属共享基础设施全局放行 |
| E56 | `text_encoding` → 无业务依赖（空表） | SH-064 编码识别：只依赖 `std`，供 `sandbox`/`tools` 共用 |
| E57 | `user_terminal` → 无业务依赖（空表） | SH-071 右侧栏独立终端：只依赖 `portable_pty`/`windows`/`std`，不进沙箱、不进模型上下文 |
| E58 | `test_support` → 无业务依赖（空表） | 测试夹具（自删临时目录）：只依赖 `std`/`ulid`；仅测试文件（`tests.rs`/`test.rs`）可反向依赖它，脚本按"目标 = `test_support` 且文件名为测试文件"窄放行，不做"所有测试文件一律豁免" |
| E59 | `images` → 无业务依赖（空表） | SH-072 图片引用与进程内字节缓存：只依赖 `serde`/`base64`/`std` 的共享叶子，`model_client` 与 `tools` 同时依赖它 |
| E60 | `media_route` → `{tool_router, workspace_files, app_state}` | SH-135 `/api/file` 媒体路由：越界判定复用 `tool_router::resolve_in_workspace`（与文件工具同判据，E30 同源理由），字节上限复用 `workspace_files::MAX_FILE_BYTES`（一个数只能有一处定义），`app_state` 只是取根集合快照与 `tauri::State` 句柄。**不反向依赖**：路由只被组合根在窗口 builder 上挂载，`tool_router`/`workspace_files` 不知道它存在；`config` 属共享基础设施全局放行 |
| E61 | `key_check` → `{model_client, app_state}` | A0-1 密钥三态校验：错误分类复用 `model_client::ModelError`（状态码 → 三态的映射只允许一处，第二套 401 判定必然与主链路漂移，与 E20 同源理由），命令壳经 `app.state::<AppState>()` 取装配状态与 DPAPI 密钥。HTTP 客户端是外部 crate `reqwest`，**不构成 crate 内边**——不要为它凭空登记网络层模块。`config` 属共享基础设施全局放行 |
| E62 | `tray_notify` → 无业务依赖（空表） | A0-2 关窗提示：在**已有托盘图标**上挂 `Shell_NotifyIcon(NIF_INFO)` 气泡，只依赖 `windows`/`std`。用 `EnumWindows` 按窗口类 `tray_icon_app` + 当前 pid 找 `tray-icon` 的消息窗口，再用 `NIM_MODIFY` 发气泡——不新增第二个图标，也不把托盘实现搬进本模块。调用方是组合根（`lib.rs` 的 `CloseRequested` 与托盘菜单），本模块不知道任何业务模块存在 |
| E63 | `clock` → 无业务依赖（空表） | R3 重复代码收敛：九份同义的 `now_ms()`（UNIX 纪元毫秒、`u64`、时钟早于 1970 回落 0）收敛为唯一出口，只依赖 `std`。它是纯叶子，任何模块依赖它都不产生反向依赖；`tests/evals_baseline.rs` 另有一份返回 `u128` 且时钟异常时 panic 的同名函数，语义不同，**不合并**（结构用例按「src 恰好一次 + tests 显式豁免」登记） |

> E11 与 E12 看似反向，实则互补：**运行时**控制流是 router 分发到工具（trait object，无编译期引用）；**编译期**依赖是工具依赖 router 的类型与注册表。两者都必须允许，否则要么工具无法实现 trait，要么 router 被迫 `use` 具体工具。

> **结构归属判定记录（SH-072，2026-11-09）**——三处曾被判违规的归属，定论如下。**后续不得把它们当违规"修"回去**：
>
> 1. **`config/model_catalog.rs` 不是独立模块，是 `config` 层内的静态数据表**。它是 `Config::builtin()` 的默认值来源（`include_str!` 一份 JSON 表 + 一个查表函数），全仓唯一消费方就是 `config` 自己，`capability` 读它也是经 `config::model_catalog` 的公开路径。单独建叶子模块只会得到一张"只有 `config` 依赖它"的边，属于把内部实现细节抬成架构节点。故它**不出现在 2.3.1 表里**：根本不存在跨模块边，也就没有需要登记的边。
> 2. **`images` 是共享叶子，承载 `ImageRef` + `image_store`**（E52–E54、E59）。若把 `ImageRef` 留在 `model_client`，`view_image` 要构造引用就必须 `tools → model_client`——那是 2.3.2 明令禁止的边。禁止边不该靠豁免活着：把两者都下沉到一个零业务依赖的叶子（`serde`/`base64`/`std`），`model_client` 与 `tools` 同时依赖它，方向立刻变干净。**不要**把 `ImageRef` 挪回 `model_client`，也不要让 `images` 反向依赖任何一方。
> 3. **`ImageBudget` 与 `attachment()` 归 `tool_router` 共享内核**（E53）。它们连接的是"工具产出引用"与"循环读回引用"两端：放 `tools` 会逼出 `agent_loop → tools` 越层，放 `agent_loop` 会让工具反向依赖循环。按 §2.3.3「跨层共享的类型放共享内核」处理，与 `ToolSpec`/`ToolContext`/`PlanState` 同一归属原则。

#### 2.3.2 明确禁止的边

| 禁止的边 | 理由 |
| --- | --- |
| `tools/*` → `model_client` / `agent_loop` / `ui` | 反向依赖：工具不得知道循环与模型的存在 |
| `agent_loop` → `tools/*` | 越层：必须经 `tool_router`；工具注册由组合根完成（`PlanState` 迁入共享内核即为此） |
| `model_client` → `tool_router` | 与 E08 成环；共享 DTO 归属地固定在 `model_client`，反向引用一律违规 |
| `permission` / `sandbox` → `agent_loop` / `tools/*` / `model_client` | 上游越界，破坏"裁决点唯一" |
| `events` / `config` → 任何业务模块 | 共享基础设施只能被依赖，不得反过来依赖业务 |
| `agent_loop` → `mcp_client` | 越层且成环：MCP 工具经 `tool_router` 进入循环，客户端装配与进程监管在组合根（E47 / 02 §3.1.5 X6） |

#### 2.3.3 三类特殊角色（不按普通分层判定）

| 角色 | 模块 | 规则 |
| --- | --- | --- |
| 共享基础设施 | `config`、`events`、`clock` | 任何模块都可依赖它们，不构成违规；它们自身不得依赖任何业务模块（`clock` 是纯叶子，只依赖 `std`，全仓唯一的「当前时间」出口） |
| 装配层 / 组合根 | `app_state.rs`、`lib.rs`、`main.rs` | 允许依赖任意模块（负责构造与依赖注入，不参与业务分层判定）；业务模块不得反向 `use app_state`/`lib` |
| 共享内核 | `tool_router` | `ToolSpec`/`ToolDeclaration` 桥接、`PlanState`、`ToolContext` 都在这一层。跨层共享的类型放这里，**不得为"就近"下沉进 `tools/*`**——会立刻逼出 `agent_loop → tools` 反向依赖（`tool_router/mod.rs:19` 注释记录了这次迁移的原因） |

> **豁免判据按模块身份，不按名字**（SH-076，2026-11-05 定稿）：`app_state` 是装配层**模块**——长成目录（`app_state/mod.rs`、`app_state/*.rs`）后整模块仍属装配层，`check-deps.ps1` 按 owner 豁免；`lib` / `main` 是 crate 根 / bin 根，Rust 里只能是文件，按顶层精确路径豁免。同名文件/目录不共享豁免（子目录里的 `lib.rs` 不会被豁免），防止"放一个文件绕过全部门禁"的假绿。

### 2.4 缝合原则（三层来源与边界）

> **判断依据（长期有效）**：SHANIU 不是从零自研，而是把三套成熟实现缝在一起。新增任何功能，先回答「这属于哪一层」；三层都不属于，才谈自研，并且必须写清理由与代价。

| 层 | 来源 | 不可越界的地方 |
| --- | --- | --- |
| 前端 / UI | **DSH**（`src/dsh/`，vendored） | 词汇表、交互形态、组件、主题令牌一律用它的；不自造外壳、不自造样式 |
| 执行骨架 / 沙箱 / 权限 | **codex** | 循环控制权归宿主（不是模型自己决定停）；命令级沙箱；策略分层；策略在执行前生效 |
| 交互归属 / 编辑实战 | **ZCode** | 审批冒烟回父会话但保留 origin 身份；8 级匹配（含剥离行号前缀、缩进弹性）；先读后写与 stale 检测 |

#### 2.4.1 自研清单（我们自己的责任）

目前只有四样。每一样上游都没有对应物，**误杀与维护成本由我们承担**：

| # | 自研项 | 为什么必须自研 | 代价 |
| --- | --- | --- | --- |
| 1 | 失败自愈闭环（测试失败 → 读错 → 修复） | 上游没有「失败后自动读错再修」的闭环 | 必须设重试上限与放弃条件，否则烧钱空转 |
| 2 | 注入检测（默认拒绝、可解释、显式启用与撤销） | 上游的 MCP 信任面不检查工具描述注入 | 规则误杀由我们处理；每次误杀都是一次人工介入 |
| 3 | 逐工具风险档位（用户指定，不采信服务器注解） | 上游把风险交给静态分类或服务器自报 | 用户要在首次批准时逐个定档，交互成本由我们承担 |
| 4 | 豁免模型（按指纹 + 工具名，指纹变化即失效） | 上游没有「按指纹失效」的豁免语义 | 指纹一变全部失效，用户需重新确认，误伤由我们承担 |

#### 2.4.2 开工前的判断流程（可执行）

按顺序回答，前一问有答案就不进入下一问：

1. **是界面/交互/组件/样式/主题令牌吗？** → 去 DSH 找对应物；有就复用，没有就先说明「为什么必须自造」再动手。
2. **是循环控制、沙箱、权限裁决、策略生效点吗？** → 按 codex 骨架实现；不得改变「策略在执行前生效」与「循环控制权归宿主」。
3. **是审批归属、编辑匹配、stale 检测吗？** → 按 ZCode 语义实现；不得弱化 origin 身份与先读后写。
4. **三层都不属于？** → 才允许自研；提交说明必须写「上游各自怎么做、选了哪个、为什么不选另一个」，以及误杀/维护成本。
5. **仍然拿不准？** → 停下问用户，不自行假设。

#### 2.4.3 退化红线

任何「取最优方案」的改动，若会让安全语义退化——例如把「拒绝」改成「提示后放行」、把「不启动」改成「先跑再问」、把「必须重批」改成「自动沿用」——**必须先说明再动手**，不得顺手做，也不得以「体验更好」为理由夹带。

## 3. 核心设计决策（ADR）

### ADR-001：Agent 主循环形态

| 驱动 | 优先级 | 依据 | 取舍 |
| --- | --- | --- | --- |
| 自主纠错需要"执行→观察→再推理"闭环 | 高 | codex `run_turn`（core/src/session/turn.rs） | 循环内嵌套流式处理增加复杂度 |
| 随时可中断 | 高 | ZCode `enqueueCancellableRuntimeCommand` | 取消传播需贯穿所有工具 |
| 上下文有限 | 高 | codex compact 模块 | 压缩可能丢失细节，需 rollout 兜底 |

**决策**：单线程逻辑循环（tokio task），每轮 = 请求模型（流式）→ 收集 tool calls → 经 permission 裁决 → 执行（支持并行只读工具）→ 结果回填 → 再请求。循环携带 `CancellationToken`；每轮采样前检查 token 预算触发 compaction。
**备选**：① 状态机驱动（ZCode TurnMachine）——表达力强但 AI 编程实现成本高，**拒绝**；② 无循环的一次性 chain——不满足自主纠错，**拒绝**。
**可逆性**：双向门。重构触发器：需要子 Agent 并行编排时升级为显式状态机。
**状态**：已决定。

### ADR-002：Windows 沙箱实现

| 驱动 | 优先级 | 依据 | 取舍 |
| --- | --- | --- | --- |
| AI 代理执行任意命令，必须真实隔离 | 高 | codex sandboxing/src/windows.rs | 实现复杂度高 |
| 全 AI 编程，需要可分阶段交付 | 高 | 一次性实现完整 ACL 引擎风险大 | 分 tier 渐进 |

**决策**：三级沙箱策略（沿用 codex 语义）——
1. `read-only`：可列目录/读文件，禁止一切写入与命令执行（不经子进程，纯策略裁决）；
2. `workspace-write`：命令经**受限令牌 + Job Object** 启动子进程，对工作区外路径写访问用 deny-ACE 封锁；网络不参与档位（命令一律可出网，2026-11-10 定）；
3. `danger-full-access`：直接执行，UI 全程显著标识。
**Fail-closed**：策略组合无法实现时报错拒绝，不降级为"提示后执行"。
**分阶段**：M1 先交付策略裁决层（逻辑边界）+ `read-only`/`danger-full-access`；M2 交付 RestrictedToken+JobObject；M3 补 deny-ACE 精细路径控制。
**备选**：① 仅提示无隔离——安全不达标，**拒绝**；② Windows Sandbox（MXC/容器）——重、依赖 Pro 版系统组件，**拒绝（首版）**，留扩展点。
**可逆性**：`sandbox` 是 ACL 防腐层，内部实现可替换。
**状态**：已决定（分阶段）。

### ADR-003：审批与权限模型

**决策**：Permission Broker 集中裁决（参考 ZCode permissionGate）。工具按风险分四级：`read`（自动放行）/ `write-in-workspace`（按沙箱模式自动或询问）/ `execute`（询问，可"本会话记住选择"）/ `destructive`（每次必问：git push --force、rm 递归、工作区外写入）。
**Plan Mode**：`EnterPlanMode` 免确认进入只读计划态；`ExitPlanMode` 必须用户确认（复用审批通道，用户可附修改意见）——语义照抄 ZCode 的 plan-mode-approval-boundary。
**审批 UI 不可伪造**：审批请求由 Rust 后端发出、经 Tauri 原生窗口事件通道，前端渲染仅展示；裁决结果只接受后端校验过的审批 ID 回执。
**状态**：已决定。

### ADR-004：工具系统与扩展

**决策**：统一 `ToolSpec`（JSON Schema）+ `ToolExecutor` trait + `ToolRouter`（照 codex 模式）。内置工具首批：`unified_exec`（命令执行，流式 stdout/stderr、超时、stdin、取消）、`apply_patch`（结构化补丁，禁止任意写文件绕过审批）、`plan`（计划模式）、`read_file/list_dir/search`（只读）、`request_user_input`。
MCP 客户端列入二期；协议上 `ToolSpec` 已兼容动态注册。
**备选**：直接 shell 自由文本写入——无法审计无法审批，**拒绝**。
**状态**：已决定。

### ADR-005：前后端通信协议

> 2026-11-06 修订：数据面传输由「Tauri emit 广播」改为**本地 WebSocket gateway**（见下）。

**决策**：
- 协议载荷不变：单一事件协议 `EventMsg`（Rust enum，serde tagged），信封按 04 §1.1（`event_id`/`session_id`/`agent_id`/`parent_id`/`ts_ms`）；事件与命令面以 04 为准。
- **数据面（事件流）**：Rust 在 loopback 起 WebSocket gateway（进程级 token 鉴权，经 `gateway_info` 命令回报前端，重连复用），按会话多路复用，消费端以 credit 背压；断线按 `event_id` 续播、缺口从事件日志（`event_journal`，非 rollout 模型历史）分页补齐。线契约见 04 §1.4（SH-094 批 2 落地服务端，批 3 切换前端；gateway 不可用时桥一次性退回 Tauri 广播作 fail-safe）。
- **控制面（低频命令）**：保留 Tauri `invoke`（send_task、approve、cancel、set_config、窗口/托盘/目录选择），不放宽 WebView 权限面。
- **时序**：adapter（SH-017）落地后接入；批 3 起桌面事件面默认走 WS，Tauri 广播只作 gateway 不可用时的兜底（一次退回、不双通道消费），payload 与 adapter 接口不因此改变。实现卡 SH-094。
- **持久化**：`rollout/` 将每轮请求/响应/工具调用写 JSONL（`RolloutItem::{ResponseItem, Compacted, SessionMeta}`），支持 fork/resume。
**为什么不再维持 Tauri 广播**：全局广播无法按会话路由（多会话/子代理并发是 M5 目标）、无背压（工具输出 burst 会堆积到 WebView），adapter 还得为全局事件总线重造流语义；WS 与 DSH 客户端原生的 gateway 流语义对齐，adapter 更薄、可多路复用、TCP 自带背压。
**代价与缓解**：端口占用/冲突（动态端口 + 启动握手回报）；鉴权（进程级 token + 仅 loopback 监听）；CSP（`connect-src` 放行 loopback）；生命周期（随 app 退出关闭，睡眠唤醒后重连）。
**备选**：① Tauri emit + 合批——改动最小但无背压、多会话仍需自造路由，**不选**；② Tauri Channel——点对点有序但仍无 TCP 级背压，**不选**（WS 落地受阻时作为回退）。
**明确不做（2026-11-08 传输层评估结论，留痕避免反复重提）**：
- 不迁移到 `tauri::ipc::Channel`——没有重放游标，会把已验证的 `event_id` 续播重做一遍，等于用更弱的语义替换已验证的实现。
- 不引入本地 HTTP 服务——多端接入没有需求，只增加鉴权面与攻击面。
- 不改 sidecar JSON-RPC——多一次进程边界序列化，当前没有独立 sidecar 的需求，收益为负。
**状态**：已落地（SH-094 批 3，2026-11-07）：服务端、前端切换、断线续播/credit 背压与真机验收均完成。

### ADR-006：前端架构（全量复刻 deepseek-harness，后端渐进接线）

> 2026-11-06 修订：原方案为"参考 DSH 模式自研"，现修订为**全量复刻 DSH 前端**。

**决策**：
- **总体策略——前端 Day-1 完整，后端渐进接线**：第一步把 DSH 前端（`apps/web` + `packages/client` 的 UI 层：`ui-primitives`/`ui-chat`/`ui-deliverables`/`store` 等）**完整**移植为 SHANIU 前端基线，React 18 → 19 升级，**全部交互逻辑原样保留**（流式增量渲染、conversation-nodes 会话组织、审批交互、diff/终端展示、快照存储），不做重新设计、不做裁剪。移植完成时整个 UI 在 mock 数据下即可完整操作。
- **渐进接线模型**：唯一对接面是 transport 注入层（对应 DSH 的 `dshDesktopBoot.ready()` 注入模式）。自研 `transport/adapter` 把 DSH 前端期望的事件/命令模型映射到 SHANIU 的 `EventMsg`/命令协议（04 文档）；后端尚未实现的能力由 `transport/stubs.ts` 提供 stub 并记入**接线清单**。之后每个后端里程碑 = 核销清单中的一批 stub，把对应 UI 交互接到真实能力上——UI 代码本身不因接线而改动。
- **设置界面不再是硬约束**：配置以 `config.toml` 为准（§9），设置 UI 降为可选增强，不进入任何里程碑验收。
- **后续演化**：用户将自行调整 UI；适配层是唯一对接面，UI 侧自由改动不触碰后端契约。
**后果**：正向=前端第一天就是完整成熟产品形态、交互经真实验证、后端可按能力独立推进；负向=DSH 事件模型与 `EventMsg` 存在阻抗差（适配层成为关键复杂点）、移植后与 DSH 上游分叉（其上游修复需手工挑选同步）。
**备选**：① 参考模式自研——重复造轮子且交互质量不可控，**拒绝**；② 直接改 DSH 源码对接后端、不设适配层——前后端协议耦合死，**拒绝**。
**可逆性**：适配层隔离下 UI 可整体替换，双向门。
**状态**：已决定（修订版）。

### ADR-007：沙箱与权限基线采用 codex 骨架

**决策**：
- **命令级沙箱**：每条命令按当前 permission profile 解析沙箱策略（对齐 codex `core/src/exec.rs` 的 `SandboxTransformRequest` 模式），不设「整个 agent 一个长期沙箱」。
- **审批策略分层**：`never` / `on-failure` / `on-request` / `full-access` 随 turn 生效，不做全局开关。
- **命令前缀白名单**：高频只读/构建命令按可配置前缀放行并留审计（对齐 codex `core/src/exec_policy.rs`），命中即不弹窗，但可从审计记录事后追溯。
**理由**：权限随命令走才能在长会话里既能收紧又能减少打断；前缀白名单是降低审批中断的结构性手段，而不是靠用户忍耐。
**代价**：前缀规则配置错误会放宽执行面。缓解：默认集只含只读/构建类；写文件、删除不得进入默认前缀；每条放行写审计。
**不采用**：全局审批开关（粒度太粗，无法按 turn 收紧）；按工具名硬编码豁免（无法表达参数差异）。
**状态**：已决定，待实现（`docs/05` SH-120）。

### ADR-008：授权规则作用域限定 `(agent_id, session)`，禁止全局落盘共享

**决策**：
- 「总是允许」按 `(agent_id, tool, 参数模式)` 分区存储；父→子单向继承，子→父默认不回灌；仅当用户显式选择「共享到父会话」时才合并。
- `resume` 取 `min(子代理原收窄集, 父当前策略)`，任一维度变严都生效；续跑不得成为提权路径。
- **明确不采用** codex 的 `ExecPolicyManager` 全局落盘 `$CODEX_HOME/rules/default.rules`，也**不采用** ZCode 共享单例 `PermissionService` 的会话级授权扩散。
**理由**：全局规则会让一次局部放行被父代理、兄弟代理与后续会话继承。ZCode 还存在 `a b` 与 `a_b` 归一成同一前缀的命名缺口；codex 的共享规则文件则把信任面扩到整个用户目录。两者都不能作为授权作用域的蓝本。
**代价**：同一工具在不同代理中可能重复询问。缓解用「批量确认 + 会话级记忆（按 agent 分区）」，**不用**全局共享抵消。
**验证**：`resume_after_parent_narrowing_cannot_widen_child`（父侧收窄后 resume 不得回宽）；子代理 `AllowAlways` 后父/兄弟调用同一工具仍被拦（permission 契约测试）。
**状态**：已决定；`resume` 交集（SH-054）与审批记忆按 `agent_id` 分域（ADR-103）已落地，负向测试已补。

### ADR-009：审批降噪策略与量化目标

**决策**（按优先级落地）：
1. **风险分级**：只读类（read/grep/list/search）默认不弹；写文件、执行命令按策略弹；破坏性操作必须弹。
2. **命令前缀白名单**：命中即放行并留审计（不弹窗，可事后查）。
3. **会话级记忆**：按 `(agent_id, tool, 参数模式)` 记住「总是允许」；子代理授权不回灌父代理。
4. **批量确认**：同一 turn 内同一工具的连续调用合并为一次确认。
5. **审批上下文完整**：来源代理、任务摘要、将要执行的具体命令/路径、风险原因一次展示。
**量化目标**：常规编码任务**每任务审批打断 ≤2 次**；由 `docs/05` SH-119 用实际会话统计验证，不接受主观「体验变好了」。
**理由**：审批疲劳是「无脑放行」的直接前置条件（§6 风险登记册）；降噪必须与风险分级同时做，否则只是把风险藏起来。
**代价**：只读默认放行依赖工具分类准确；分类拿不准时回退到询问，绝不允许默认放行写/执行/删除。
**状态**：已决定，待实现（`docs/05` SH-118/119）。

### 9.3 数据目录解析（启动时）

按优先级解析，首个命中生效，解析结果写入日志第一行：

| 优先级 | 条件 | 数据根目录 |
| --- | --- | --- |
| 1 | 环境变量 `SHANIU_DATA_DIR` 已设置 | 该路径（用于测试/CI/多实例隔离，不读不写记录） |
| 2 | 该 exe 目录已有数据根记录 | 记录里的路径；**之后一律按记录走，不再探测**（记录在 `%LOCALAPPDATA%\SHANIU\data-root\<exe目录 hash>.json`） |
| 3 | 首次判定：exe 同目录存在 `portable.marker`，**或已存在 `<exe 目录>\data\`** | `<exe 目录>\data\`（便携模式） |
| 4 | 首次判定：上面都没有，但 exe 目录可写 | `<exe 目录>\data\`（便携模式，单文件 exe 走这条） |
| 5 | 默认 | `%APPDATA%\SHANIU\` + `%LOCALAPPDATA%\SHANIU\`（安装模式） |

第 2 层不能省：没有它，"把带 `data\` 的整个文件夹搬到新位置"会被当作首次启动重新判定；第 3 层的"已存在 `data\`"同理——少了这一层，程序会在旧数据旁边另建一套。判定只做一次并落记录，实现见 `config.rs:1495` `decide_root`（记录路径 `:1412`，可写探测 `:1444`）。

**边界规则**：
- **默认工作区固定为 `<数据根>\Workspace`**（安装版 `%LOCALAPPDATA%\SHANIU\Workspace`，便携版 `<exe>\data\Workspace`）；启动时与其余子目录一并幂等创建。用户另行指定的工作区不受此约束。
- **过宽根直接拒绝授权**：用户显式把工作区根、`cwd` 或 `allowed_roots` 指向用户主目录、盘符/共享根、`%SystemRoot%`、`%ProgramFiles*` 时，授权被拒并写进 `acl-audit.jsonl` 与状态面（提示「请改选它下面的具体项目目录」）；主目录的子目录照常放行，工具链目录（可能本就在 `Program Files` 下）不受此约束，也不提供一键豁免开关。判定与实现见 `docs/04` §1.5.1。
- 沙箱 `workspace-write` 的作用域 = `<用户工作区>`。**目标状态（未实现，待办）**：SHANIU 自身数据目录（安装版的 `%APPDATA%`/`%LOCALAPPDATA%`，便携版的 `data\`）应对 Agent 拒绝读写（防止 Agent 篡改自身配置/密钥/日志）；**唯一例外是默认工作区子树 `<数据根>\Workspace`**——它本身就是 Agent 可写作用域，拒绝清单必须放行该子树。便携模式下 Agent 工作区若为 `SHANIU-Portable` 的父目录，必须把 `data\` 显式加入拒绝清单但仍放行 `data\Workspace`。
  - **当前不满足**：2026-11-11 只读核查确认代码中没有对应的拒绝 ACE 或等效拦截，Agent 在 `workspace-write` 下的实际可达范围以已落盘的 ACE 为准。写成已完成会直接误导审计，所以保留为待办。
  - **落地验收**：Agent 在 `workspace-write` 下尝试写 `<数据根>\config.toml` 必须失败并留下拒绝记录；写 `<数据根>\Workspace\` 下的文件必须成功。两条都通过后，本节改回陈述语气。
- `secrets\` 只能由 `config.rs` 读写；DPAPI 加密**绑定当前机器当前用户**——便携版整体拷贝到另一台机器后密钥不可解密，启动时检测解密失败则标记密钥失效并引导用户重新输入（fail-closed，不回退为明文存储）。
- `logs\` 与 `rollouts\` 落盘前统一过脱敏过滤器（见风险登记册 R2）。
- 便携版常位于可移动/未加密介质：首次启动便携模式时提示一次数据落盘位置与加密建议（如 BitLocker To Go），用户可关闭提示。
- 两种形态共用同一构建产物与同一套代码路径，差异仅在数据根目录解析；禁止为便携版维护独立代码分支。

### 9.4 构建与发布路径（唯一正确姿势）

- **正式发布必须走 `pnpm tauri build`**；裸 `cargo build --release` 不可分发（见下条）。
- `src-tauri/Cargo.toml` 声明 `custom-protocol = ["tauri/custom-protocol"]`，**不设 default**。原因：`tauri-codegen` 用该 feature 决定 `generate_context!` 是**内嵌 `frontendDist`** 还是**走 `build.devUrl`**（`dev = cfg!(not(feature = "custom-protocol"))`）。缺该项时 `cargo build --release` 产出的 exe 会去连 `http://localhost:5173`，dev 服务器未运行即表现为**永久白屏**（2026-11-08 实测确认，不是"白屏一段时间"）。不设 default 是因为 default 生效后，任何 `cargo check/clippy/test` 都要求 `dist/` 已存在（`tauri-codegen` 在 `frontendDist` 缺失时直接 panic），而 CI 与本地都是先跑 cargo 检查再 `pnpm build`。
- 手工构建 release（需要可分发 exe 时）：先 `pnpm build`，再 `cargo build --release --features custom-protocol`；`tauri dev` 由 CLI 自带 `--no-default-features`，继续走 dev 服务器热更新。
- 验证口径：启动产物后经 CDP `/json` 确认 `url` 为 `http://tauri.localhost/`（内嵌）而非 `http://localhost:5173/`，且界面有实际内容。
- 注意：`pnpm build` 更新 `dist/` 后，cargo 可能仍判定 crate 为 Fresh 而不重新内嵌资源；需 touch `src-tauri/src/lib.rs`（`cargo clean -p shaniu` 实测不可靠）后再编。

### 9.5 启动性能基线（2026-11-08 本机实测）

口径：Rust `Instant` 打点 + 前端 `performance.now()` + Navigation/Paint Timing，按 `performance.timeOrigin` 对齐进程时钟。数值为多次运行的区间，非估算。

| 阶段 | 打包版（7 次） | dev 冷加载 |
| --- | --- | --- |
| 进程启动 → 窗口对象创建（`setup_enter`） | 215–246 ms | 234 ms |
| 窗口 → 页面开始加载 | +12–15 ms | +80 ms |
| HTML 解析 → 主包执行完成 | +158–167 ms | +2769 ms（250 个模块请求） |
| 首次绘制 FCP | ≈+170 ms | 2872 ms |
| boot 完成（挂载） | 634–738 ms | 3184 ms |
| 首帧（挂载后双 rAF） | 647–764 ms | 3417 ms |

- **主导因素**：打包版无单一瓶颈，三分——窗口/WebView2 创建 ≈0.23 s、主包取回解析 ≈0.17 s、boot ≈0.21 s（其中 `ipc_get_product_dirs` 94–201 ms、`mount_sync` 34–51 ms、`layout` 28–52 ms）。dev 冷加载 81% 花在 Vite 逐模块转译，与产品代码无关。
- **两种白屏并存（改前）**：`0–≈230 ms` 无窗口；`≈230 ms–FCP` 为 WebView2 默认纯白（窗口 `backgroundColor` 已设为 `#151517`）；`FCP–首帧` 为深色背景但 `#root` 为空（`index.html` 无骨架）。2026-11-08 起由 9.5.1 的"窗口延迟显示 + L0/L1"关闭，复测见该节。
- **首屏门控只有一个**：`applyProductWorkspacePath()` 的 IPC；**没有**等 WS 建连、没有等 `load_session` 返回才渲染。
- **bundle 事实**：主 chunk 4836.8 KB 单文件（`src/dsh` 上游包经 `vite.config.ts` 的 aliases 全部并入，无独立 vendor chunk），CSS 517 KB 单文件；其余 128 个 asset 多为按需加载的 shiki 语法包。
- **未归因样本（保留待查）**：2026-11-08 09:05:01 一次运行首帧 11.9 s，其中"HTML 解析 → 主包执行"占 9.7 s；8 s 时 `module_started=false` 证明应用 JS 尚未开始执行。同构建 3 次复测未重现（均 0.65–0.68 s），**无逐项证据，不归因于产品代码，也不视为已解决**。若再现，按 WebView2 进程启动 / JS code cache / 磁盘与杀软扫描三条线分别取证。
- **明确暂不做**（已评估，避免重复提议）：
  1. 拆主 chunk / vendor 分包：46 个 feature 全静态 import，改动面大，等主循环稳定后再评估。
  2. `index.html` 内联骨架：遮丑不治病，会让"看起来好了"与"真的就绪"更难区分。
  3. splash 窗口：把白屏换成一张图，首帧时间不变，且多一个窗口要维护。
  4. 拆分 `mount_sync`：DSH 单次 mount 语义，容易引入槽位边界问题。
  5. 把 `ipc_get_product_dirs` 移出首屏关键路径：**查过了，不能简单挪**。`homeDir` 在挂载前被两处消费——`root.provide('connection', hostServices(homeDir).connection)`（`connection` 是 46 个 feature 安装期就 `inject` 的服务，晚提供需要引入占位/可观测服务）与 `setDefaultWorkspacePath(dir.workspaceRoot)`（会话默认工作区基线，晚写会让首帧创建的会话落到错误根目录）。约 100 ms 收益换状态不一致风险，不做。
- **已知限制**：① 全部测量在 `--remote-debugging-port` 下进行，对冷态可能有放大；② 真冷启动（重启 + 杀软全盘扫描 + WebView2 运行时冷加载）未覆盖，本机只做到清 WebView2 profile 与结束 webview 进程；③ "窗口首次可见"无直接打点，`setup_enter` 仅为上界（Tauri 在调用用户 setup 之前已创建配置窗口），改后以 Rust 就绪日志 + 页面 FCP 夹逼；④ 窗口 `backgroundColor` 固定为主题暗色基色：正常路径下窗口在启动页画好之后才显示，该底色只在 3 s 兜底强制显示时才可能被看到（浅色主题下这一次可能是暗底），未跟随主题；⑤ 阶段反馈的起点是主包执行到 `main.tsx`，dev 模式实测主包加载占 3.1 s，这段只有呼吸点、没有阶段文案——该区间没有可靠进度源（250 个模块请求的完成数不是可展示的阶段），不编造。

#### 9.5.1 启动加载态（L0–L3，2026-11-08 落地）

设计目标不是"更快"，是**全程没有一帧是错的**：不出现 WebView2 纯白帧、不出现空 `#root` 帧、不出现启动页→首屏的跳变。

| 层 | 实现位置 | 内容 | 时机 |
| --- | --- | --- | --- |
| L0 | `index.html` `<head>` 内联脚本 + `<style>` | 按上次解析结果（`localStorage['shaniu.theme.resolved']`，缺省读 `prefers-color-scheme`）预涂 `--boot-bg`（暗 `#151517` / 浅 `#fff`），并同步给 `body` 打 `data-ds-dark-theme` | 任何脚本执行前 |
| L1 | `index.html` `#root` 内静态标记 | 字标 + 单个呼吸点（1.6 s；`prefers-reduced-motion` 下退化为静态） | HTML 解析即出现，无 JS |
| L2 | `src/host/boot-progress.ts` | 只报真实阶段：`准备工作区` / `装载界面插件 X/46` / `渲染界面`；<250 ms 不揭示，揭示后每段至少停 300 ms | 仅在超过阈值时出现 |
| L3 | `src/main.tsx` + `BootProgress.done()` | 启动页先提到 `body`（React 首次提交会清空 `#root`，留在里面会被瞬间删掉），应用首帧后同底色交叉淡入 160 ms 再移除 | 挂载完成 |

- **窗口延迟显示**：`tauri.conf.json` `visible: false`；`index.html` 解析结束（双 rAF）调 `frontend_ready` 显示窗口，`main.tsx` 就绪后再调一次兜底；Rust 侧另有 3 s 强制显示兜底（`lib.rs`，`FRONTEND_READY` 原子位 + `async_runtime::spawn`）。
- **失败出口三层**，都不出现"永久转圈"：① `boot-progress` 8 s 未就绪 → 诊断面板（标题 / 原因 / `停在：<阶段>` / 日志路径 / 重试按钮）；② `index.html` 12 s 看门狗兜"主包根本没执行"（内嵌资源损坏、模块加载失败），主包接管后调 `window.__shaniuBootSettle()` 撤销；③ 窗口显示 3 s 兜底。
- **代价（如实）**：淡出 160 ms 与已可交互的应用重叠（`done()` 一进入就设 `pointer-events: none`），不增加可用时间；正常冷启动从 `createBootProgress` 到挂载 <250 ms，阶段文案根本不出现，零成本；慢启动时启动页因"最短可见 300 ms"最多多留 300 ms，但输入已在就绪瞬间放行。
- **不要抄的**：环形进度（上游依赖 Cordis fiber 计数，本机 209 ms 里只走十几度）、多段轮播文案、无真实比例的进度条、骨架屏、独立 splash 窗口（与延迟 show 重复）。

复测（同机、打包版、7 次；"页龄"= `performance.now()`，即从页面开始加载起算）：

| 指标 | 改前（9.5 表） | 改后 |
| --- | --- | --- |
| FCP | ≈+170 ms | +120–128 ms |
| 启动页首现 | 无 | +50–52 ms |
| 应用首帧（挂载、开始淡出） | 634–738 ms | +560–576 ms |
| 启动页完全移除（视觉交接完成） | 无 | +727–734 ms（落在改前首帧区间 647–764 内） |
| dev（Vite 冷加载） | FCP 2872 / 首帧 3417 | FCP 136 / 挂载 3442 / 移除 3607（250 个模块请求不变，见限制⑤） |

- **逐帧证据**（CDP `Page.startScreencast`，逐帧算平均亮度）：打包版暗色 64 帧 21.7–27.3（0 帧 >200，即无纯白帧），浅色 71 帧 252–255（0 帧 <200，即无暗帧），dev 341 帧全暗；过渡帧中应用首屏已完整、字标在淡出，**不存在"启动页撤了、应用没画上"的空帧**。
- **窗口显示与首帧的先后**：Rust 日志 `前端就绪信号到达，显示主窗口` 在 gateway 监听后 +85–101 ms，与页面 FCP（页龄 120–128 ms）基本同刻——窗口真正可见时启动页已经画好，"先 show 再加载纯白页"的路径不存在（这也是先验证、再决定做不做启动页的依据）。
- **失败路径实测**：`Network.setBlockedURLs` 阻断主包 → 12 s 出现"启动没有完成 / 停在：加载界面代码 / 日志…/ 重试"；`Page.navigate about:blank` 让页面完全不加载 → Rust 日志 `WARN 前端未在 3 秒内发出就绪信号，强制显示主窗口`，窗口 `visibilityState` 变 `visible`。
- **主题跟随**：静态 `index.html` 读不到宿主设置，用"上次解析结果 + `MutationObserver` 跟随每次主题切换写回"；浅色路径用 CDP 模拟 `prefers-color-scheme: light` 实测，从第一帧起就是 `#fff`，无先暗后亮。限制：切换主题后若在写回前强杀进程，下次启动会沿用旧主题渲染启动页，随后被应用主题纠正（一帧级错配）。
