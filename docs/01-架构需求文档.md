## 1. 项目概述

SHANIU 是一款 **Windows 桌面 Agent Harness 客户端**：在本地托管自主编码 Agent 的完整生命周期——任务输入、模型推理循环、工具执行、沙箱隔离、人工审批、流式渲染与会话持久化。

| 项 | 值 |
| --- | --- |
| 技术栈 | Tauri 2.12.5 + React 19.3.1 + Rust 1.99.1 + Vite 8.3.5 |
| 目标平台 | Windows 10/11 x64（首发，架构上保留跨平台沙箱扩展点） |
| 进程模型 | 单进程：Tauri Rust 后端承载全部 Agent 逻辑，WebView 前端通过 IPC 通信 |
| 开发方式 | 全部代码由 AI 编码代理产出，受 `AGENTS.md` 约束 |

### 1.1 目标（Goals）

- G1：提供完整的自主编码循环——用户下达任务后，Agent 自主规划、读写文件、执行命令、自我纠错，直到任务完成或被中断。
- G2：**真实沙箱**，不是"仅提示"——Windows 上通过受限令牌（Restricted Token）+ Job Object + ACL 实施文件系统/网络边界；策略无法满足时拒绝执行（fail-closed）。
- G3：风险分级审批——只读工具自由执行，写入/命令按沙箱策略与审批模式裁决，破坏性操作必须人工确认。
- G4：流式体验——模型输出、命令输出、diff 全部流式渲染，支持随时中断（CancellationToken）。
- G5：会话可恢复——rollout 持久化（JSONL），支持 fork/resume/replay。

### 1.2 非目标（Non-Goals）

- 不做多用户/协作/云端同步（单机单用户）。
- 不做自有模型推理，仅对接兼容 OpenAI Responses/Chat Completions 协议的远端或本地端点。
- 首版不做 MCP 市场/插件 UI 沙箱（保留协议扩展点，见 ADR-004）。
- 不打包子 Agent 并行编排（`multi_agents` 列入二期候选）。

| `events` | 事件协议定义+广播 | Rust | 全部 | `ui` | shared kernel | `EventMsg` → Tauri Event 序列化 |

### 2.3 依赖方向规则（不可违反）

`ui → events`；`agent_loop → {model_client, tool_router, rollout, events}`；`tool_router → tools/*`；`tools/* → {permission, sandbox}`；**禁止反向依赖，禁止 `tools/*` 直接访问 `model_client` 或 `ui`**。

> 上述一行是规则摘要；**完整清单以下面 2.3.1 的允许边表为准**——摘要表漏登的边若出现在 2.3.1，即视为合法（例如 `agent_loop → permission`、`tool_router → model_client`）。

#### 2.3.1 允许的边（全量清单）

> **本表是 FF-1（依赖方向不变量：违规数 = 0）的唯一事实来源**：规则变更必须先改本节、再改脚本，禁止反过来——先改脚本等于把架构规则藏进脚本，评审看不见，必然与本文档漂移。
> **现状（实然）**：`scripts/check-deps.ps1` 按本表**正向校验**（白名单 + fail-closed）：表外模块判违规并提示先在本节登记；`config`/`events` 为共享基础设施、任何模块可依赖且自身只依赖二者；`lib.rs`/`main.rs`/`app_state.rs` 为组合根，跳过判定。
> **为什么用白名单**（SH-076，已随 SH-009 落地 2026-11-05）：黑名单的失效模式是**静默豁免**——新模块天然落在规则之外，坏边一条不报而 CI 照样绿；多报一条能被看见，漏报一条没人知道。

#### 2.3.2 明确禁止的边

| 禁止的边 | 理由 |
| --- | --- |
| `tools/*` → `model_client` / `agent_loop` / `ui` | 反向依赖：工具不得知道循环与模型的存在 |
| `agent_loop` → `tools/*` | 越层：必须经 `tool_router`；工具注册由组合根完成（`PlanState` 迁入共享内核即为此） |
| `model_client` → `tool_router` | 与 E08 成环；共享 DTO 归属地固定在 `model_client`，反向引用一律违规 |
| `permission` / `sandbox` → `agent_loop` / `tools/*` / `model_client` | 上游越界，破坏"裁决点唯一" |
| `events` / `config` → 任何业务模块 | 共享基础设施只能被依赖，不得反过来依赖业务 |

#### 2.3.3 三类特殊角色（不按普通分层判定）

| 角色 | 模块 | 规则 |
| --- | --- | --- |
| 共享基础设施 | `config`、`events` | 任何模块都可依赖它们，不构成违规；它们自身不得依赖任何业务模块 |
| 装配层 / 组合根 | `app_state.rs`、`lib.rs`、`main.rs` | 允许依赖任意模块（负责构造与依赖注入，不参与业务分层判定）；业务模块不得反向 `use app_state`/`lib` |
| 共享内核 | `tool_router` | `ToolSpec`/`ToolDeclaration` 桥接、`PlanState`、`ToolContext` 都在这一层。跨层共享的类型放这里，**不得为"就近"下沉进 `tools/*`**——会立刻逼出 `agent_loop → tools` 反向依赖（`tool_router/mod.rs:19` 注释记录了这次迁移的原因） |

> **豁免判据按模块身份，不按名字**（SH-076，2026-11-05 定稿）：`app_state` 是装配层**模块**——长成目录（`app_state/mod.rs`、`app_state/*.rs`）后整模块仍属装配层，`check-deps.ps1` 按 owner 豁免；`lib` / `main` 是 crate 根 / bin 根，Rust 里只能是文件，按顶层精确路径豁免。同名文件/目录不共享豁免（子目录里的 `lib.rs` 不会被豁免），防止"放一个文件绕过全部门禁"的假绿。

## 3. 核心设计决策（ADR）

### ADR-001：Agent 主循环形态

| 驱动 | 优先级 | 依据 | 取舍 |
| --- | --- | --- | --- |
| 自主纠错需要"执行→观察→再推理"闭环 | 高 | codex `run_turn`（core/src/session/turn.rs） | 循环内嵌套流式处理增加复杂度 |
| 随时可中断 | 高 | ZCode `enqueueCancellableRuntimeCommand` | 取消传播需贯穿所有工具 |
| 上下文有限 | 高 | codex compact 模块 | 压缩可能丢失细节，需 rollout 兜底 |

**决策**：单线程逻辑循环（tokio task），每轮 = 请求模型（流式）→ 收集 tool calls → 经 permission 裁决 → 执行（支持并行只读工具）→ 结果回填 → 再请求。循环携带 `CancellationToken`；每轮采样前检查 token 预算触发 compaction。
**备选**：① 状态机驱动（ZCode TurnMachine）——表达力强但 AI 编程实现成本高，**拒绝**；② 无循环的一次性 chain——不满足自主纠错，**拒绝**。
**可逆性**：双向门。重构触发器：需要子 Agent 并行编排时升级为显式状态机。
**状态**：已决定。

### ADR-002：Windows 沙箱实现

| 驱动 | 优先级 | 依据 | 取舍 |
| --- | --- | --- | --- |
| AI 代理执行任意命令，必须真实隔离 | 高 | codex sandboxing/src/windows.rs | 实现复杂度高 |
| 全 AI 编程，需要可分阶段交付 | 高 | 一次性实现完整 ACL 引擎风险大 | 分 tier 渐进 |

**决策**：三级沙箱策略（沿用 codex 语义）——
1. `read-only`：可列目录/读文件，禁止一切写入与命令执行（不经子进程，纯策略裁决）；
2. `workspace-write`：命令经**受限令牌 + Job Object** 启动子进程，对工作区外路径写访问用 deny-ACE 封锁，网络默认禁用；
3. `danger-full-access`：直接执行，UI 全程显著标识。
**Fail-closed**：策略组合无法实现时报错拒绝，不降级为"提示后执行"。
**分阶段**：M1 先交付策略裁决层（逻辑边界）+ `read-only`/`danger-full-access`；M2 交付 RestrictedToken+JobObject；M3 补 deny-ACE 精细路径控制。
**备选**：① 仅提示无隔离——安全不达标，**拒绝**；② Windows Sandbox（MXC/容器）——重、依赖 Pro 版系统组件，**拒绝（首版）**，留扩展点。
**可逆性**：`sandbox` 是 ACL 防腐层，内部实现可替换。
**状态**：已决定（分阶段）。

### ADR-003：审批与权限模型

**决策**：Permission Broker 集中裁决（参考 ZCode permissionGate）。工具按风险分四级：`read`（自动放行）/ `write-in-workspace`（按沙箱模式自动或询问）/ `execute`（询问，可"本会话记住选择"）/ `destructive`（每次必问：git push --force、rm 递归、工作区外写入、网络上传）。
**Plan Mode**：`EnterPlanMode` 免确认进入只读计划态；`ExitPlanMode` 必须用户确认（复用审批通道，用户可附修改意见）——语义照抄 ZCode 的 plan-mode-approval-boundary。
**审批 UI 不可伪造**：审批请求由 Rust 后端发出、经 Tauri 原生窗口事件通道，前端渲染仅展示；裁决结果只接受后端校验过的审批 ID 回执。
**状态**：已决定。

### ADR-004：工具系统与扩展

**决策**：统一 `ToolSpec`（JSON Schema）+ `ToolExecutor` trait + `ToolRouter`（照 codex 模式）。内置工具首批：`unified_exec`（命令执行，流式 stdout/stderr、超时、stdin、取消）、`apply_patch`（结构化补丁，禁止任意写文件绕过审批）、`plan`（计划模式）、`read_file/list_dir/search`（只读）、`request_user_input`。
MCP 客户端列入二期；协议上 `ToolSpec` 已兼容动态注册。
**备选**：直接 shell 自由文本写入——无法审计无法审批，**拒绝**。
**状态**：已决定。

### ADR-005：前后端通信协议

> 2026-11-06 修订：数据面传输由「Tauri emit 广播」改为**本地 WebSocket gateway**（见下）。

**决策**：
- 协议载荷不变：单一事件协议 `EventMsg`（Rust enum，serde tagged），信封按 04 §1.1（`event_id`/`session_id`/`agent_id`/`parent_id`/`ts_ms`）；事件与命令面以 04 为准。
- **数据面（事件流）**：Rust 在 loopback 起 WebSocket gateway（一次性 token 鉴权，随 AppHandle 注入），按会话多路复用，消费端以 credit 背压；断线按 `event_id` 续播、缺口从 rollout 分页补齐。
- **控制面（低频命令）**：保留 Tauri `invoke`（send_task、approve、cancel、set_config、窗口/托盘/目录选择），不放宽 WebView 权限面。
- **时序**：adapter（SH-017）落地前不实现；切换前事件仍走 Tauri 广播作为过渡，payload 与 adapter 接口不因此改变。实现卡 SH-094。
- **持久化**：`rollout/` 将每轮请求/响应/工具调用写 JSONL（`RolloutItem::{ResponseItem, Compacted, SessionMeta}`），支持 fork/resume。
**为什么不再维持 Tauri 广播**：全局广播无法按会话路由（多会话/子代理并发是 M5 目标）、无背压（工具输出 burst 会堆积到 WebView），adapter 还得为全局事件总线重造流语义；WS 与 DSH 客户端原生的 gateway 流语义对齐，adapter 更薄、可多路复用、TCP 自带背压。
**代价与缓解**：端口占用/冲突（动态端口 + 启动握手回报）；鉴权（一次性 token + 仅 loopback 监听）；CSP（`connect-src` 放行 loopback）；生命周期（随 app 退出关闭，睡眠唤醒后重连）。
**备选**：① Tauri emit + 合批——改动最小但无背压、多会话仍需自造路由，**不选**；② Tauri Channel——点对点有序但仍无 TCP 级背压，**不选**（WS 落地受阻时作为回退）。
**状态**：已决定（方向）；实现排 SH-094。

### ADR-006：前端架构（全量复刻 deepseek-harness，后端渐进接线）

> 2026-11-06 修订：原方案为"参考 DSH 模式自研"，现修订为**全量复刻 DSH 前端**。

**决策**：
- **总体策略——前端 Day-1 完整，后端渐进接线**：第一步把 DSH 前端（`apps/web` + `packages/client` 的 UI 层：`ui-primitives`/`ui-chat`/`ui-deliverables`/`store` 等）**完整**移植为 SHANIU 前端基线，React 18 → 19 升级，**全部交互逻辑原样保留**（流式增量渲染、conversation-nodes 会话组织、审批交互、diff/终端展示、快照存储），不做重新设计、不做裁剪。移植完成时整个 UI 在 mock 数据下即可完整操作。
- **渐进接线模型**：唯一对接面是 transport 注入层（对应 DSH 的 `dshDesktopBoot.ready()` 注入模式）。自研 `transport/adapter` 把 DSH 前端期望的事件/命令模型映射到 SHANIU 的 `EventMsg`/命令协议（04 文档）；后端尚未实现的能力由 `transport/stubs.ts` 提供 stub 并记入**接线清单**。之后每个后端里程碑 = 核销清单中的一批 stub，把对应 UI 交互接到真实能力上——UI 代码本身不因接线而改动。
- **设置界面不再是硬约束**：配置以 `config.toml` 为准（§9），设置 UI 降为可选增强，不进入任何里程碑验收。
- **后续演化**：用户将自行调整 UI；适配层是唯一对接面，UI 侧自由改动不触碰后端契约。
**后果**：正向=前端第一天就是完整成熟产品形态、交互经真实验证、后端可按能力独立推进；负向=DSH 事件模型与 `EventMsg` 存在阻抗差（适配层成为关键复杂点）、移植后与 DSH 上游分叉（其上游修复需手工挑选同步）。
**备选**：① 参考模式自研——重复造轮子且交互质量不可控，**拒绝**；② 直接改 DSH 源码对接后端、不设适配层——前后端协议耦合死，**拒绝**。
**可逆性**：适配层隔离下 UI 可整体替换，双向门。
**状态**：已决定（修订版）。

## 9. 产品目录结构（安装与运行时）

产品提供两种发行形态：**安装版（MSI）**与**便携版（ZIP，免安装）**。两者共用同一套数据目录布局，仅根目录不同，由启动时的目录解析逻辑决定（见本节末尾）。

### 9.1 安装版（MSI）

安装目录与运行时数据严格分离；卸载默认保留用户数据，提供"同时删除数据"选项。

```
├── crash\                        # 崩溃转储（待用户确认后才可上报）
└── Workspace\                    # 默认工作区（Agent 操作目录；用户可在界面另行指定）

<用户工作区>\                     # Agent 操作的项目目录（用户指定）
└── .shaniu\                      # 工作区级数据（可选）
    ├── plan.md                   #   Plan Mode 已批准计划
    └── ignore                    #   Agent 不可读路径清单（追加于沙箱策略之上）
```

### 9.2 便携版（ZIP，免安装）

```
SHANIU-Portable\                  # 解压即用，可整体放在 U 盘/同步盘
├── SHANIU.exe                    # 主程序（与安装版同一构建产物）
├── resources\                    # 前端打包产物、内置资产
├── portable.marker               # 便携模式标记文件（存在即启用便携模式）
└── data\                         # 全部用户数据，等价于安装版 %APPDATA% + %LOCALAPPDATA% 之和
    ├── config.toml
    ├── secrets\                  # API Key（见边界规则第 4 条）
    ├── settings-backup\
    ├── sessions\
    ├── rollouts\
    ├── logs\
    ├── cache\
    ├── crash\
    └── Workspace\                # 默认工作区（Agent 操作目录）
```

### 9.3 数据目录解析（启动时）

按优先级解析，首个命中生效，解析结果写入日志第一行：

| 优先级 | 条件 | 数据根目录 |
| --- | --- | --- |
| 1 | 环境变量 `SHANIU_DATA_DIR` 已设置 | 该路径（用于测试/CI/多实例隔离） |
| 2 | exe 同目录存在 `portable.marker` | `<exe 目录>\data\`（便携模式） |
| 3 | 默认 | `%APPDATA%\SHANIU\` + `%LOCALAPPDATA%\SHANIU\`（安装模式） |

**边界规则**：
- **默认工作区固定为 `<数据根>\Workspace`**（安装版 `%LOCALAPPDATA%\SHANIU\Workspace`，便携版 `<exe>\data\Workspace`）；启动时与其余子目录一并幂等创建。用户另行指定的工作区不受此约束。
- 沙箱 `workspace-write` 的作用域 = `<用户工作区>`，SHANIU 自身数据目录（安装版的 `%APPDATA%`/`%LOCALAPPDATA%`，便携版的 `data\`）**默认对 Agent 拒绝读写**（防止 Agent 篡改自身配置/密钥/日志）；**唯一例外是默认工作区子树 `<数据根>\Workspace`**——它本身就是 Agent 可写作用域，拒绝清单必须放行该子树。便携模式下 Agent 工作区若为 `SHANIU-Portable` 的父目录，必须把 `data\` 显式加入拒绝清单但仍放行 `data\Workspace`。
- `secrets\` 只能由 `config.rs` 读写；DPAPI 加密**绑定当前机器当前用户**——便携版整体拷贝到另一台机器后密钥不可解密，启动时检测解密失败则标记密钥失效并引导用户重新输入（fail-closed，不回退为明文存储）。
- `logs\` 与 `rollouts\` 落盘前统一过脱敏过滤器（见风险登记册 R2）。
- 便携版常位于可移动/未加密介质：首次启动便携模式时提示一次数据落盘位置与加密建议（如 BitLocker To Go），用户可关闭提示。
- 两种形态共用同一构建产物与同一套代码路径，差异仅在数据根目录解析；禁止为便携版维护独立代码分支。
