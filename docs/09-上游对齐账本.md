## 1. 账本怎么读

每个条目七个字段：

| 字段 | 含义 |
| --- | --- |
| `upstreamPath` | 上游相对路径（`packages/client/...`）；上游没有则为 `null` |
| `ourPath` | 本地相对路径（`src/dsh/packages/client/...`）；本地没有则为 `null` |
| `status` | 机械判定，四值，见下表 |
| `review` | `recorded`（有 `align/overrides.json` 人工记录）/ `needs-review`（没有，必须补） |
| `reason` | 为什么这样；**只来自 overrides.json，脚本不编** |
| `guard` | 下次同步上游时该怎么做；同上 |
| `upstreamHash` / `ourHash` | 内容 sha256（行尾已归一，见 §2）；缺文件为 `null` |

`status` 四值：

| status | 判据 | 补法 |
| --- | --- | --- |
| `same` | 两边都有，哈希相同 | 无需动作 |
| `drift` | 两边都有，哈希不同 | **合并**上游变更，保留本地补丁，回写 docs/07 |
| `missing` | 上游有、本地没有 | **决定要不要 vendor**（整包未接线 → 记 `not-applicable`；包内缺文件 → 真缺口） |
| `not-applicable` | 本地有上游没有（本地新增），或 overrides 显式豁免 | 无 |

`missing` 与 `drift` 的补法方向相反，**所以判定里不许互相顶替**：把"上游有、我们没有"写成 `drift` 会让人去合并一个本地不存在的文件；反过来把内容不同写成 `missing` 会让人整份覆盖掉本地补丁。

`needs-review` 是第五种状态，但它**不占用 `status`**，而是独立成 `review` 列。理由：`needs-review` 问的是"有没有人工记录"，不是"文件属于哪一类"。两者塞进同一个字段，`drift` / `missing` 的计数就会永远是 0，账本立刻失去意义。首轮实测确认过这个塌陷：混用时输出 `drift=0 missing=0 needs-review=617`。

## 2. 重跑与确定性

```powershell
pnpm align:report                      # 主入口（package.json 的 scripts）
node scripts/align-report.mjs          # 等价直调（不依赖 pnpm）
```

- 上游路径可用 `DSH_UPSTREAM` 覆盖，默认 `D:\AI\deepseek-harness`。
- **生成是幂等的**：同一份上游 + 同一份本地代码，重复跑不产生任何 diff（`git diff --stat align/` 为空），两次 `ledger.json` 的 sha256 相同（实测 `8B73BAEF…94D8C2`）。条目按路径排序、JSON 不含时间戳、不含绝对路径。
- 哈希口径：**先做行尾归一（CRLF → LF）再算 sha256**。两个仓库都检在 Windows 上，`core.autocrlf` 与编辑器保存策略不一致会让同一份内容一个 CRLF 一个 LF；按原始字节算会把检出差异报成 `drift`（首轮实测 3 个假阳性：`ui-settings-models` 的 `ModelRow.tsx` / `ModelsSection.module.css` / `locales.ts`，字节差恰好等于换行增量）。行尾不是内容，单列不计入账本。
- 构建产物与依赖不进账本：`node_modules`、`dist`、`build`、`coverage`、`.turbo`、`.vite`、`.cache`、`.git`。
- `reason` / `guard` 只能来自 `align/overrides.json`；脚本没有记录时**不许兜底成"看起来合理"的说明**，一律打 `needs-review`。

## 6. 附：录制回放可行性（只读调查，未实现）

**判定：上游侧「可行」；照搬到我们这侧「有条件可行」。**

上游证据（基线 `fcc0ad4621`）：

| 能力 | 落点 | 说明 |
| --- | --- | --- |
| 录制 / 刷新 / 回放开关 | `DSH_SNAPSHOT=record\|refresh\|replay` | replays 是默认（`test:snapshot` 不写盘） |
| 回放执行器 | `packages/test-support/session-snapshot` | 会话 JSONL 既是输入也是期望输出 |
| 已入库 fixture | `snapshots/{session,web,acp,sdk}` | `snapshots/web/approval-composer/` 有 `session.v4.jsonl` + `ui.expected.md` + `workspace.expected/` |
| 事件流回放 | `snapshots/session/headless.snapshot.ts`（83 KB） | headless 驱动会话的现成入口 |
| LLM 侧回放 | `packages/test-support/llm-replay`、`llm-mock-server`（`pnpm mock:llm`） | 不烧 token、不依赖外部端点 |
| 客户端侧 harness | `packages/test-support/{client-runtime,remote-mock}` | 浏览器域事件流可编排 |
| e2e 通道 | `pnpm test:e2e`（真 API）、`pnpm test:web`（含 keyless 回放场景） | 两套分开，回放不花钱 |

结论依据：这不是"能不能做"的问题——上游已经把「脚本化跑一个场景 → 事件流落成 fixture → 无密钥回放比对」做成了基础设施，并且规定了硬约束（`snapshots/AGENTS.md`）：被测进程只能经 `dsh` CLI + 出厂 profile 启动，**禁止**另加入口、隐藏 CLI 模式或可执行的场景驱动。

对我们这侧的三个前提：

1. **不能直接驱动我们的应用**：上游的驱动入口是 Node 的 `dsh` CLI，我们的宿主是 `src-tauri`（Rust + WebView2）。`snapshots/` 那套跑的是上游进程，直接拿来跑 SHANIU 跑不起来。
2. **能复用的是 fixture，不是 runner**：把上游 `snapshots/session/*/session*.jsonl` 当 canonical 事件流喂给 `src/transport/adapter.ts`，可以验证"同一条上游事件流，我们的 journal 重建结果是否与 DSH 一致"。这条路径不需要 headless 浏览器，成本最低，建议先做。
3. **要驱动我们的 UI 才需要新增能力**：Tauri + WebView2 的 headless 驱动需要 WebDriver（`tauri-driver` + `msedgedriver`），当前仓库没有任何 playwright / e2e 配置（已核）。在 `AGENTS.md` §10 的资源优先级下（自主编码能力优先、界面打磨后置），这属于后置项。

若要把「录制」也搬过来（在我们这侧产生 fixture），还差一件事：我们的 rollout JSONL 与上游 session JSONL 不是同一格式，需要一层转换或直接用 `event_journal` 投影，且必须遵守 §3 数据边界（会话档案视同敏感数据，截取前脱敏并获许可）。
