# 祖先前置权限（Traverse）落地方案决策材料

状态：**决策材料，未动手**（2026-11-12）。相关实现与本文限制同步记录在 `docs/04-协议规范.md` §1.5.1。

## 一、要解决的问题（一句话）

workspace-write 容器要在祖先目录上有「路过 + 读属性」权限；`C:\`、`C:\Users`、盘根这类层级只有 SYSTEM/Administrators 能改 DACL，**非提权用户运行时补不上**，冷构建依旧失败。运行期补写实测 86s/次且对非提权完全无效，已从 exec 路径撤回。

## 二、现状边界（实测，不美化）

| 事实 | 数据 |
| --- | --- |
| 非提权能改的祖先 | `%USERPROFILE%`、`AppData`、`AppData\Local`、`%TEMP%`、工作区自身 |
| 非提权改不了的祖先 | `C:\`（owner=TrustedInstaller）、`C:\Users`（Administrators 可写，当前进程 Administrators 为 deny-only）、盘根 `D:\`；审计实测 `result:"denied"`（err 5） |
| 写一条不继承 ACE 的代价 | 系统要重算整棵子树。逐级：`C:\Users\<user>` 62.4s、`AppData` 30.5s、`AppData\Local` 13.4s、`AppData\Local\Temp` 1.4s；快照 0–1ms、备份 0ms，时间全在 `SetNamedSecurityInfoW` |
| 端到端影响 | 单次 spawn（进程内首次 workspace-write）中位 **11.6s → 86.4s**，最差 163.6s；退出还原中位 86.0s（5 次实测） |
| 关键否定证据 | 真机实测（单次）：把 `Traverse` 成功写进 `%USERPROFILE%`（审计 ok）后，容器仍 `metadata` 不到它——路径解析在 `C:\Users` 就断了。**所以运行期补写对非提权用户完全无效**，对管理员也只是多花 86s |
| 结论 | 运行期不做祖先写入（已撤回）；只有安装期一次预置才可能既有效又不贵 |

固定 SID 的可行性：exec 容器名固定为 `Shaniu.Sandbox.v1`，AppContainer SID 由名字确定性派生，**所有机器一致**——安装期可以精确写出这一条 ACE。（MCP 容器 SID 由 server id 派生，安装期不知道，仍需运行期处理；其祖先通常落在用户可写层级，且同样受盘根两级的限制。）

## 三、三条路子

| # | 方案 | 做法 | 工期 | 风险 |
| --- | --- | --- | --- | --- |
| A | **安装期预置（正解）** | MSI/安装器的提权自定义动作，给 `C:\`、`C:\Users`、各固定盘根写一条**不继承**的 `Traverse` ACE（trustee = 固定容器 SID）；卸载时按同一 SID 精确删除 | **2–3 人日**（含安装/卸载/回滚/校验用例） | ① 安装后才新增的盘（U 盘、后挂载卷）没有预置，仍不可用；② 企业组策略/安全基线可能拒绝写盘根 DACL（安装要可回滚）；③ 预置点必须可枚举，否则卸载残留 |
| B | **首次运行一次性提权** | 首次启动弹一次 UAC，跑内置 `sandbox-prep` 子命令做与 A 相同的写入；结果落标记文件 | **1–2 人日** | ① 用户拒绝 UAC = 仍然坏，必须明确提示；② 杀软/EDR 对「应用自提权改盘根 ACL」敏感，易被标记；③ 与 A 不冲突，可作 A 失败时的兜底 |
| C | **放弃 AppContainer 读隔离**（对齐 dsh 的 WRITE_RESTRICTED） | 只用受限令牌 + Job，不再需要祖先 traverse | **1–2 人日**（含探针/文档改写） | 产品边界倒退：读隔离（SH-021）与 loopback 隔离一起失效，沙箱只剩写约束。**不建议**，仅登记 |

## 四、结论

1. **A 是正解**：一次性、可枚举、可卸载；预置之后运行期在那些层级变成 `has_explicit_grant` 幂等跳过，86s 的重传播代价同时消失。
2. B 作为 A 的兜底（非 MSI 安装形态、或安装期被策略拒绝时使用），不单独作为方案。
3. C 是唯一「不碰盘根」的替代，但代价是删掉读隔离——不划算。
4. **没有第四条能同时保留读隔离、又不碰盘根的路子**：路径解析要求「路过的每一级」都能读属性，而工作区的祖先是用户不可选的（`C:\Users\<user>\...` 由系统决定）。把产物目录搬到容器自有目录只能解决 temp/构建缓存，解决不了工作区本身。
5. **已经排除的第四条**：运行期由 app 自己补祖先 ACE。实测 86s/次且对非提权无效，已撤回代码调用（机制与降级审计保留）。

## 五、本次范围

运行期机制（`ancestor_chain` / `grant_chain` / 降级审计 / 按深度还原）已实现并有用例，但**不在 exec 路径上调用**；A/B/C 均**未实施**，等待决策。

机制验证口径：`grant_chain_covers_ancestors_and_restores_them` 只在 `%TEMP%` 下自造三层链条（上界钉在临时根，**不向盘根写**），验证「可写祖先真的被加上 `Traverse`、没被升级成可列举、退出后按备份逐级还原」。反向对照已跑：去掉祖先段 → 该用例在「祖先应有 Traverse ACE」处变红；`Traverse` 放宽为 `FILE_GENERIC_READ | FILE_GENERIC_EXECUTE` → 在「不得升级成可列举/可读」处变红。

降级分支的端到端证据是真机审计（对 `C:\`、`C:\Users` 的写入被拒，`result:"denied"`，err 5），本机无法在可写层级内造出「`WRITE_DAC` 被拒且可恢复」的目录（给自己加 Deny 会连恢复一起锁死），该分支由 `degrade_only_for_ancestor_chain_and_access_denied` 的判定单测覆盖。
