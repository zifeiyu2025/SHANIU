两处**不当成产品 bug**的环境事实：

1. 用 `Start-Process` 启动的 `SHANIU.exe` 约 10s 后被回收，日志停在「前端就绪」，无崩溃记录。原因是 Trae Shell 命令 job 结束时连带杀子进程；改用 WMI `Win32_Process.Create` 脱离 job 后稳定运行。**这是自动化环境问题，不是产品崩溃。**
2. 添加提供商弹层里，按无障碍树 `click` 输入框会导致弹层关闭，最终用 `set_value` 写入各字段。**这是自动化驱动限制**；但「1296×809 下表单被裁切、需要滚动」是产品侧体验问题，见 §6。

## 1. 任务一：临时工程里做一个小改动并跑对应测试

**我想做什么**：新建会话（testproj 工作区）→ 让 agent 修 `src/stats.js` 里 `mean` 的两个 bug（空数组应抛 `RangeError`；分母应为 `values.length`）→ 跑测试。

**实际发生了什么**

1. 默认档位「仅可查看」下，agent 读文件正常，写文件/执行命令直接被拒，它回了一句「需要你放开权限」并停下（截图 `shots\05-readonly-blocked.png`）。切到「工作区内修改」后重新发起，改动落盘（磁盘核对：`if (values.length === 0) throw new RangeError(...)`，分母改为 `values.length`，`median` 未动）。
2. 跑测试失败：`node --test` 报 `spawn EPERM (errno -4048)`，末行 `[sandbox] mode=workspace_write enforcement=full denied=piped-stdio`；`npm test` 同因失败（`shots\07-node-test-sandbox-denied.png`）。另有一次弹出 cmd 窗口显示 `[出现错误 2147942632 (0x800700e8) (启动"cmd /C node --test"时)]`。
3. agent 改用 `node test/stats.test.js` 跑通 4/4。同一台机器上不受沙箱约束的 Shell 里 `node --test` 也是 4/4，确认不是代码问题。

**是否卡住**：改动本身没卡住（切档后一步到位）；**跑测试这条线被沙箱堵住**，只能换写法绕过。

**复现步骤**

1. 默认「仅可查看」新建会话，要求「修 src/stats.js 并运行测试」→ 观察被拒并索要权限。
2. 切「工作区内修改」，再次要求修改 → 改动成功。
3. 要求原样运行 `node --test` → 观察 `denied=piped-stdio` / `spawn EPERM`；`npm test` 同。

**严重度**：高（阻断「改完就跑测试」的主线工作流；`package.json` 里写的就是 `node --test`，默认跑不通）。

## 2. 任务二：触发需要审批的写入/危险命令

**我想做什么**：验证审批卡可见、可点、拒绝与同意都能正常收口。

**实际发生了什么**

1. 审批卡正常出现（`shots\06-approval-card.png`）：风险类型 `execute:unified_exec` / `write`，按钮「拒绝」「允许一次」「总是允许」。
2. **拒绝**：点「拒绝」后 agent 立即停止，不重试，回合正常收口（界面显示「已完成，用时 42 秒」），没有卡在「正在调用工具」。
3. **同意**：点「允许一次」后命令执行；同一工具换参数会再次审批；`Remove-Item -Recurse -Force` 这类危险命令同样先弹卡（`shots\08-approval-outside-write.png`）。
4. **工作区外写入**：向 `scratch\gui-026\outside\probe.txt`（测试当时的临时路径，已随目录清理）写入审批被允许后，`mkdir` 报「拒绝访问」、直接写文件报「系统找不到指定的路径」，`probe.txt` 未创建；agent 如实报告「未创建」，没有绕过、没有谎报。

**是否卡住**：不卡。**但审批语义与实际能力不一致**：用户点了「允许」，动作仍然必失败，界面没有任何「沙箱不允许」的解释。

**复现步骤**：读取模式下要求写工作区外路径 → 审批卡出现 → 点「允许一次」 → 观察 `mkdir 拒绝访问` / `系统找不到指定的路径`。

**严重度**：中高（会让人误以为工具坏了；同一张卡上「允许」对工作区外写入是无效承诺）。

## 3. 任务三：长会话 + 上下文压缩后的连贯性

**我想做什么**：把上下文推到压缩阈值，观察压缩是否触发、压缩后对话是否连贯、是否丢内容。

**实际发生了什么**

1. 阈值 20000（测试配置）。日志：`turn=1 input_tokens=22342` → `上下文已压缩（SH-032） compressed_items=89 history_len=17`；下一轮 `input_tokens=10600`。事件流里有配对的 `compaction_started`（`range 0..89`, `estimated_tokens=22342`, `budget_tokens=20000`, `trigger=pressure`）与 `compaction_ended`（`ok=true`, `history_tokens_after=4710`）。
2. rollout 里写入了 `type=compacted` 锚点（第 128 行），`summary` 结构 = 「用户原文（逐字保留）+ 分隔线 + 5 项摘要」，5 项齐全，用户早期硬约束（只读/切档/原样跑 `node --test`/不要改文件）都在。
3. 压缩后追问「只凭记忆回答：改的是哪个文件哪个函数、改了哪两处、测试怎么跑通的、之前失败过什么」——四项全部答对（含 `denied=piped-stdio`、`spawn EPERM` 这些细节）。**连贯性达标，未发现丢内容。**

**是否卡住**：不卡。但有两个可见性问题：

- **运行中压缩完全无声**：界面没有任何提示/分隔线，只有「上下文已用 2% → 1%」这种百分比变化，用户无从知道发生过一次有损压缩（`shots\11-post-compaction.png`）。
- **重启后历史被整体替换**：重启前 12 轮 39 步，重启后 6 轮 12 步，压缩前的多轮对话被**一条巨大的「用户原文 + 摘要」消息**替换，内部提示语「## 用户原文（压缩时逐字保留，不得改写）」原样显示在对话里（`shots\12-restart-compacted-history.png`）。这符合 04 §6.4 的 resume 重放语义（**设计如此**），但用户视角是「历史不可回看 + 内部字段外泄」。

**复现步骤**：`token_budget` 调到 20000 → 连续多轮把 input_tokens 推过阈值 → 看日志/事件流 → 追问关键事实 → 重启后看时间线轮数与内容。

**严重度**：中（功能正确，信息可见性不足）。

## 4. 任务四：关窗、重开、重连

**我想做什么**：检查运行态显示与实际是否一致，回合有没有被错误收口或凭空补结束。

**实际发生了什么**

1. **正常关窗**：关窗不退出，进系统托盘（日志：`关窗提示已发到系统托盘气泡 running=1`），后台回合继续并正常完成。
2. **运行中关窗再重开**：10s 内重开，界面正确显示「深度求索中，用时 23 秒」与「停止生成」，随后生成完成（7 轮 27 步），正文完整、无重复段落、没有凭空补结束（`shots\10-reopen-while-running.png`）。
3. **强制结束进程后重启（崩溃场景）——高严重度问题**：
   - 上一回合界面已明确显示「已完成，用时 2 秒」，`events.jsonl` 里也有 `turn_completed reason=completed`。
   - 任务管理器强杀后重启，该回合被标成「已停止 / 任务已停止 / DSH 进程在本轮完成前退出（例如被强制结束、崩溃或关闭超时），重新启动后本轮已中止。未完成的工具调用结果未知。」
   - 同一条横幅**重复出现两次**，轮次计数从「1 轮 1 步」变成「2 轮 2 步」（凭空多一轮一步）。
   - 在**新会话、从未压缩、仅一轮「只回复：hi」**的条件下稳定复现，与压缩无关；正常关窗走托盘不触发。
   - 证据：`shots\13-abort-after-crash.png`（新会话复现）、`shots\12-restart-compacted-history.png`（压缩会话同样两处横幅）。

**是否卡住**：不卡，但状态是错的。

**复现步骤**：新会话 → 发「只回复：hi」→ 等界面显示「已完成，用时 N 秒」→ 任务管理器强制结束 SHANIU.exe → 重新启动 → 看时间线顶部与末尾。

**严重度**：高（已完成的工作被判「结果未知」，用户会误以为白做；横幅重复 + 凭空加轮次，属于「运行态显示与实际不一致」的正面案例）。

## 5. 任务五：默认档位第一次使用

**我想做什么**：看默认档位下第一次使用会不会被莫名卡住，或该拦的没拦。

**实际发生了什么**

- 默认「仅可查看」：首轮任何写入/执行都被拒，agent 只能反问「请放开权限」，**界面没有就地升级入口的引导**（用户得自己找到输入框旁的「访问模式」按钮）。`shots\05-readonly-blocked.png`
- 默认审批 `on_request`：连 `mkdir`、`if not exist` 这种只读判断也逐条弹审批，长任务里点卡次数偏多。
- **未发现该拦没拦**：工作区外写入、递归删除都先审批且沙箱另有硬拦，没有越权执行成功的情况。

**判断**：两个都是设计选择（安全默认），但首次使用的落差与审批频次属于体验问题，不是「不可用」。

**严重度**：低-中（体验）。

## 7. 结论

### 真机做成了的任务

| 任务 | 结果 |
|---|---|
| 1. 临时工程小改动 + 跑测试 | **做成但有折中**：改动成功；`node --test`/`npm test` 被沙箱拒绝，靠 `node test/stats.test.js` 验证 4/4 |
| 2. 审批（拒绝/同意/危险命令） | **做成**：卡可见可点，拒绝与同意都正常收口；工作区外写入批准后仍被沙箱硬拦且如实上报 |
| 3. 长会话 + 压缩连贯性 | **做成**：压缩真实触发（22342 → 10600 tokens），锚点完整，压缩后关键事实全部答对，未丢内容 |
| 4. 关窗/重开 | **正常关窗做成**；**强制结束后重启的状态显示是错的**（见下） |
| 5. 默认档位 | **观察完成**：无越权，但首轮被拦无引导、审批偏密 |

### 没做成的

- **`npm test` / `node --test` 在工作区内修改档下不可用**（`denied=piped-stdio`），只能换写法。
- **崩溃/强杀后重启，已完成回合被误报为「已中止」**，横幅重复两次并凭空多出一轮一步。
- **「允许」审批对工作区外写入无实际效力**，且界面不解释。

### 最需要先修的三个问题

1. **崩溃恢复把已完成回合判成「已中止」（P0）**：`events.jsonl` 里有 `turn_completed reason=completed`，重启后仍显示「本轮已中止、工具结果未知」，且横幅重复、轮次 +1。新会话一轮即可复现（`shots\13-abort-after-crash.png`）。修复口径：以该回合的 `turn_completed` 为准，只有存在未收口的 `turn_started` 才打中止横幅，并且只打一次。
2. **沙箱 `denied=piped-stdio` 让标准测试命令失效（P0/P1）**：`package.json` 默认 `node --test`，在「工作区内修改」档下必失败，等于「改完不能跑测试」。要么放开子进程管道，要么在失败时给出可执行的就地处置（例如自动回退并明确说明），而不是让模型自己猜着换写法（`shots\07-node-test-sandbox-denied.png`）。
3. **审批语义与沙箱能力不一致（P1）**：工作区外写入点「允许一次」后依旧必然失败（`拒绝访问` / `系统找不到指定的路径`），审批卡等于给了无效承诺。要么在卡上直接标「该路径沙箱不可写」并禁用允许，要么让批准真正提升该路径的写权限（`shots\08-approval-outside-write.png`）。

紧接着值得处理的一项是**压缩的可见性**：运行中不提示、重启后整段历史被摘要替换且把「## 用户原文（压缩时逐字保留）」这种内部提示语展示给用户（`shots\11-post-compaction.png`、`shots\12-restart-compacted-history.png`）。功能是对的，呈现需要补。
