## 0. 一页结论

**目标机制一句话**：`workspace-write` 子进程改用 `CreateRestrictedToken(DISABLE_MAX_PRIVILEGE | LUA_TOKEN |
WRITE_RESTRICTED)`，restricting 列表为 `[logon SID, Everyone, 工作区写 SID, temp 写 SID]`；只在
**工作区根 / TEMP / 工具链目录**写一条可继承的 allow ACE；读、网络、祖先目录一律不碰，所以不需要管理员。

**删除清单规模**：函数/类型级 86 项 → **整删 30 / 保留 41 / 改造 15**；文件级 2 个整删（`appcontainer.rs`、
`device_acl.rs`）+ 1 个测试文件整删。

**三步验收**（详见 §7，每步都含真机）：
1. **令牌本体**：真机跑出「区内写成功 / 区外写失败 / 区内 `cargo test` 跑通」。
2. **旁路迁移**：MCP、终端、孙进程、出网四条真机通过，且第二次启动不再写 DACL。
3. **默认切换 + 回退开关**：新档默认、旧档 `sandbox.os="app_container"` 一键切回仍能跑；连过之后再删旧机制。

**落地方式有一处与「一次性删干净」不同**：删除清单按 **A 新增并存 → B 切默认 → C 删旧** 三期执行。
理由见 §7 开头——用户新增的硬要求是「保留一键切回旧机制的配置项，直到新机制真机连续验过」，
一次性删掉旧机制会让这条要求无处落地。删除清单本身不变，只是加了执行顺序和门禁。

## 1. 目标机制的精确定义

### 1.1 令牌：标志位与 restricting 列表

**【代码】codex**

- `D:\AI\codex\codex-rs\windows-sandbox-rs\src\token.rs:500`
  `let flags = DISABLE_MAX_PRIVILEGE | LUA_TOKEN | WRITE_RESTRICTED;`
- 同文件 `:481-497`：restricting SID 的**精确顺序**是 `Capabilities..., ExtraRestricting..., Logon, Everyone`，
  `SID_AND_ATTRIBUTES.Attributes` 全为 `0`（普通 restricting 条目，不是 `SE_GROUP_ENABLED`）。
- 同文件 `:512-519`：令牌建好后立刻 `set_default_dacl(new_token, psid_logon)`，
  再 `enable_single_privilege(SeChangeNotifyPrivilege)`；任一步失败 `CloseHandle` 并返回错误（fail-closed）。
- 同文件 `:473-475`：capability SID 列表为空直接报错，不做「空列表退化」。

**【代码】dsh**

- `src/dsh/packages/sandbox/sandbox-windows-acl/src/token.ts:230-238`
  `DISABLE_MAX_PRIVILEGE | WRITE_RESTRICTED`，禁用 SID 列表与删除特权列表都为空。
- 同文件 `:224-228`：read-only 用 `[logon, Everyone]`；workspace-write 用
  `[logon, Everyone, ...writeSids]`，且 `writeSids` 为空时**直接抛错**。
- 同文件 `:181-206` 注释解释了为什么 `logon + Everyone` 两个都要在：早期 DLL 初始化（0xC0000142）、
  CNG（`\Device\CNG`，pwsh 崩 0xE0434352）都依赖它们。
- 同文件 `:156-165`：dsh 额外把 token integrity 降到 Low（`S-1-16-4096`），并在目录上打 no-write-up 标签。

**选型（本方案）**：跟 codex，用 `DISABLE_MAX_PRIVILEGE | LUA_TOKEN | WRITE_RESTRICTED`，**不降 integrity**。

理由：
1. 降 integrity 要改**用户目录的 mandatory label**（dsh `acl.ts:160-201`），而且要求目录 owner 且带
   `WRITE_OWNER`（dsh `acl.ts:366-370` 自己写了这个前提）——这是对用户数据目录的安全属性做持久修改，
   比「写一条 ACE」侵入大得多。
2. `LUA_TOKEN` 已让管理员组变成 deny-only，与降 integrity 在「写约束」这一目标上等价；
   该收的口子由 `WRITE_RESTRICTED` 的 pass-2 收。
3. 用户裁定「不比参考项目严格」——不追加 codex 没有的机制，正好符合。

**【代码·本仓现状】** `src-tauri/src/sandbox/windows_impl.rs:173-187`：现有 `create_restricted_token`
的标志位是 `CREATE_RESTRICTED_TOKEN_FLAGS(0)`，**没有** `WRITE_RESTRICTED`，**也没有任何 restricting SID**，
只做了「删特权，留 `SeChangeNotifyPrivilege`」。也就是说当前的 `Logical` 档并不是「写受限」，
只是「无管理员特权」——`mod.rs:111-117` 把它自报成 `partial` 是准确的。

> 结论：本方案的核心工作量不是「从零写令牌」，而是**给已有令牌补 flags + restricting SID + default DACL，
> 再补写权限授予**。这部分照抄 codex/dsh，不新造。

### 1.2 工作区写 SID 怎么来

**【代码】dsh（推荐照抄）** `src/dsh/packages/sandbox/sandbox-windows-acl/src/workspace-sid.ts:35-40`

```ts
const digest = createHash('sha256').update(workspaceRoot, 'utf8').digest()
const first  = (digest.readUInt32LE(0) % (2 ** 30 - 1)) + 1
const second = (digest.readUInt32LE(4) % (2 ** 30 - 1)) + 1
return `S-1-4-${first}-${second}`
```

- temp 用同法但加域分隔第三位：`S-1-4-x-y-1`（`workspace-sid.ts:49-53`）。
- 同文件 `:1-23` 注释写明设计理由：同一个工作区**跨会话/跨重启派生同一个 SID**，ACE 只物化一次；
  后续靠「exact-ACE skip」保持 O(1)。目录改名会派生新 SID，旧 ACE 变成惰性残留。
- 输入必须是**规范化路径**（注释 `:16-23`），否则同一目录两种拼写 → 两个 SID。

**【代码】codex（备选）** `D:\AI\codex\codex-rs\windows-sandbox-rs\src\cap.rs:16-33` 定义
`CapSids { readonly, workspace, workspace_by_cwd, writable_root_by_path }`；`:57-85` 从
`codex_home/cap_sid`（JSON）读取或**随机生成**持久化。随机 + 落盘，需额外文件与并发读写的容错。

**选型**：用 dsh 的确定性派生（`S-1-4-x-y`），不引入新的 SID 账本。

理由：本仓已经因为「账本与实际 DACL 漂移」付过代价（`mod.rs:373-375` 明确写「账本只用于自报与回滚，
判定必须按真实 DACL 探测」）。确定性派生让账本对 SID 的依赖归零：路径 → SID 是纯函数，
重建机器/重装后仍然一致。codex 的持久化方案是为它的 elevated 后端（真实沙箱用户账户）服务的，
我们没有那个后端，抄它只会多一个状态文件。

**必须做**：路径先规范化（`GetFinalPathNameByHandle` 或 `std::fs::canonicalize` 去掉 8.3 短名/大小写差异），
再做哈希。**这是唯一新增的正确性要求**，写进实现验收。

### 1.3 写什么 ACE

**【代码】dsh** `src/dsh/packages/sandbox/sandbox-windows-acl/src/acl.ts:405-412`

```
DENY_ACCESS   Everyone  FILE_DELETE_CHILD  CONTAINER_INHERIT_ACE
GRANT_ACCESS  <writeSid> GRANT_MASK        SUB_CONTAINERS_AND_OBJECTS_INHERIT
```

- `GRANT_MASK = (FILE_GENERIC_WRITE | DELETE | FILE_DELETE_CHILD) & ~STANDARD_RIGHTS_WRITE`
  （`win32-abi.ts:28`，注释 `:25-27` 明确「`WRITE_DAC`/`WRITE_OWNER` 被排除，防止子进程改 DACL 越狱」）。
- 幂等：先读 DACL，命中「完全相同的 allow ACE + deny + label」就只释放描述符、不调
  `SetNamedSecurityInfoW`（`acl.ts:386-395`）——写 DACL 会触发整棵子树继承重算，这是性能命脉。

**【代码】codex** `windows-sandbox-rs\src\acl.rs:517`

```
WRITE_ALLOW_MASK = FILE_GENERIC_READ | FILE_GENERIC_WRITE | FILE_GENERIC_EXECUTE | DELETE
```

- `:536-547`：刷新判定里把 `FILE_DELETE_CHILD` 当 `disallow_mask`——**不授 delete-child**。
- `:549-581`：`ensure_allow_mask_aces_with_inheritance_impl` 走 get-merge-set，保留已有 deny ACE。

**选型**：沿用本仓现有 `Access::Write` 掩码，即
`FILE_GENERIC_READ | FILE_GENERIC_WRITE | FILE_GENERIC_EXECUTE | DELETE | FILE_DELETE_CHILD`
（`sandbox/acl.rs:93-99`），**不改掩码**；`SUB_CONTAINERS_AND_OBJECTS_INHERIT`（`acl.rs:52`）不变。

理由：
1. 这是 dsh 的 grant 侧口径（它给 write SID 授 delete-child），能力更足，符合「harness 追平」。
2. codex 不授 delete-child，会让「删 DACL 受保护的历史文件」失败；自用场景下这类目录（如从 zip 解出、
   带保护 DACL 的工程）并不罕见，属于无谓卡点。
3. **不抄 dsh 的 `DENY Everyone FILE_DELETE_CHILD`**（`acl.ts:408`）。那条会改动**非沙箱进程**在用户
   工作区里的删除能力，属于动别人；codex 没有这个动作。本仓旧模型（AppContainer 只隔离读）在工作区内
   本来也有同样的 ambient delete-child 面，**不是回归**，因此不引入。

**必须做**：授写位置仍然只限 `acl::write_scope()` 返回的目录（`acl.rs:115-124`：工作区根、`TEMP`/`TMP`、
`temp_dir()`、`CARGO_HOME`/`RUSTUP_HOME`/`PNPM_HOME`/`NPM_CONFIG_PREFIX`、用户目录下的工具链路径），
并保留 `drop_nested`（`acl.rs:160`）与「过宽根」拒绝（`acl.rs:873`）。

### 1.4 temp 怎么处理

**【代码】dsh**：每个会话 `mkdtempSync(join(tmpdir(), 'dsh-'))` 建**私有** temp 目录，
派生独立 temp SID、单独授权，dispose 时撤销 ACE 并删目录
（`src/dsh/packages/sandbox/sandbox-local/src/index.ts:406-455`、`:460-486`）。

**【代码】codex**：`TEMP`/`TMP` 环境变量指向的目录直接进「可写根」列表（`windows-sandbox-rs\src\allow.rs`
的 writable roots + exclude 逻辑）。

**选型**：跟 codex——**不建私有 temp**，直接把写 ACE 加在 `TEMP`/`TMP`/`temp_dir()` 上
（`write_scope` 已经这么列，`acl.rs:119-124`）。

理由：
1. dsh 的私有 temp 需要一套会话生命周期（创建、授权、撤销、删目录、失败回收 `index.ts:440-455`），
   而我们没有 dsh 的 provider dispose 钩子；引入它等于新增一个可能泄漏 ACE 和目录的路径。
2. 用户裁定不比参考严格；codex 的 temp 语义就是「TEMP 可写」。
3. 代价：同工作区的多次运行共享 temp 写权（本身就是同一用户）；**不同工作区也共享 `%TEMP%` 写权**。
   这条与 codex 相同，记为已知边界（§6 第 6 条）。

### 1.5 默认 DACL（最容易漏、漏了就整条命令跑不起来）

**【代码】dsh** `token.ts:96-145` 注释与实现：受限令牌继承用户的 default DACL，而那份 DACL 里**没有**
restricting SID；子进程新建**匿名管道**（`CreatePipe`，例如 PowerShell 的管道）时，pass-2 检查失败。
dsh 的修法是在**继承的** default DACL 上合并 write SID 的 `FILE_ALL_ACCESS`（`:112-145`），失败即抛
（`:105-107` 写明 fail-closed）。注意它**修不到 libuv 的命名管道**：dsh 的 `README.zh.md:188`
把「受限孙进程的管道 stdio 捕获」登记为不可用；本仓 2026-11-13 令牌级实测同结论，见 §10.7。

**【代码】codex** `token.rs:56-62`（任务给定引用；本机没有 codex 源码，未能核对行号）：
`set_default_dacl` 是 logon 全权 + OWNER RIGHTS 读控制，即**替换**现有 default DACL，不是合并。

**选型**：跟 codex，构造 logon SID 全权 + OWNER RIGHTS 读控制（替换式，`windows_impl.rs:430-461`）。
理由：logon SID 本来就在 restricting 列表里，匿名管道等「新建时无显式 SD」的对象靠它过 pass-2；
`SetTokenInformation(TokenDefaultDacl)` 失败必须中止 spawn。

**【已验证】** 本仓 `spawn_restricted_command` 的 stdout/stderr 管道由**父进程** `CreatePipe` 创建
（`windows_impl.rs:487-493`：`SECURITY_ATTRIBUTES` 只开继承、`lpSecurityDescriptor` 为空）、
以可继承句柄传入，子进程只是使用已打开的句柄，所以「父建管道」这一步不触发 pass-2；匿名管道的 DACL
由 default DACL 提供，这正是上面两步必须保留的理由。孙进程**自己新建命名管道**是另一回事，见 §10.7。

### 1.6 进程树与 Job Object

**【代码·本仓】** `sandbox/windows_impl.rs:338-350` 创建 Job 并设 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`；
`:364-365` 用 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` 做句柄白名单；`:377-395`
`CREATE_SUSPENDED` → `CreateProcessAsUserW` → `AssignProcessToJobObject` → `ResumeThread`。

**结论：保留，不动。** 新模型只换令牌内容，Job 与句柄白名单与写约束正交。
codex 用 job-list 进程属性在创建时入 Job（`windows-sandbox-rs\src\process.rs` 的属性表），
我们是「创建后、恢复前」入 Job，语义等价，不为此改结构（重复造轮子没有收益）。

### 1.7 读、网络、路径边界的最终形态

| 维度 | 旧（AppContainer） | 新（受限令牌） | 依据 |
|---|---|---|---|
| 文件读 | 容器 SID 只读到显式授权处 | **用户可读即可读，无 OS 限制** | codex 不授 deny-read 时不加读约束；dsh read-only 才用 `[logon, Everyone]` |
| 文件写 | 只有工作区/temp/工具链 | 只有 `write_scope()` 里的位置（pass-2 收口） | §1.3 |
| 网络 | 容器能力 `internetClient`，一律出网 | 不做策略维度，走用户令牌出网 | `mod.rs:312-313`、`src/sandbox-status/wire.ts:8-9` |
| 祖先目录 | 必须写 `(RA,S)` 才能 `stat` | **完全不需要** | 读不再受限 |
| 管理员 | `C:\Users` 级需要 | **不需要** | 工作区根/`%TEMP%` 属当前用户，owner 有 `WRITE_DAC` |

**【推断（未验证）】** 出网在受限令牌下不受影响：`WRITE_RESTRICTED` 作用于文件对象访问检查的
pass-2，与 socket 无关；但本仓旧测试 `container_reaches_internet_without_any_grant`
（`tests/sandbox_probe.rs:402`）是在容器里验的，换令牌后必须重验。验证方法：真机 `Invoke-WebRequest`。

## 4. 配置与数据迁移

### 4.1 `OsSandbox` 怎么变

现状：`config.rs:975-984`

```rust
pub enum OsSandbox { #[default] AppContainer, Logical }   // serde snake_case
```

目标：新增 `RestrictedToken`，三值并存一个过渡期。

```rust
pub enum OsSandbox {
    AppContainer,      // 过渡期保留：一键回退开关（C 期删）
    Logical,           // 过渡期保留：读入后归一化为 RestrictedToken（C 期删）
    #[default]
    RestrictedToken,   // 新机制：写受限令牌 + 写 ACE
}
```

**老配置怎么读**（A/B 期，`lib.rs:3114` 附近做归一化）：
- `app_container` → A 期照旧走容器（并存验证）；B 期若字段值为 `app_container` 则**尊重它**，
  保持回退可用（这正是用户要的「一键切回」）。
- `logical` → 归一化为 `restricted_token`，打一条 `warn!`（一跑就生效，比旧档强，用户无感）。
- 缺字段 → `Default`。

**为什么保留旧变体而不是直接删**：`SandboxConfig` 用 `#[serde(default)]`（`config.rs:967`），
**未知字段**会被忽略，但**未知枚举值**会反序列化失败，可能整份配置回落到默认，用户会丢设置。
保留变体是成本最低、可逆的做法（推断：需确认 config 加载失败时的回落路径，见 §8-B）。

### 4.2 默认档位

- `SandboxMode`（`config.rs:993-1000`）**不改**：仍默认 `read_only`，workspace-write 由用户/会话选择。
  本次只换「workspace-write 用什么 OS 机制」，不动「默认策略」这条产品决策。
  > **2026-11-14 后记**：本节结论已被默认档位对齐取代——`SandboxMode` 默认改为
  > `workspace_write`（对齐 codex Auto），OS 机制不变。见 `align/permission-presets.md` §11。
- `OsSandbox` 默认值：A 期仍 `app_container`；B 期起 `restricted_token`（一行 `#[default]` 的挪动）。

### 4.3 账本与审计

| 文件 | 处理 | 理由 |
|---|---|---|
| `sandbox/ancestor-ace.jsonl` | **保留、停止追加祖先记录** | 里面记着「我们在哪级祖先加过 ACE、加之前有没有」，**卸载/回滚还要用它撤**；新机制不再产生新记录。不删是因为删了就再也找不到那些 ACE 的位置 |
| `sandbox/acl-audit.jsonl` | **保留、继续写** | 审计仍是「谁在什么时候给哪条路径授了什么」的唯一真实记录；新记录里 trustee 变成长 `S-1-4-x-y` |
| `sandbox/acl/*.dacl`（快照/备份） | **保留** | 作用域写权限仍走 `grant_guarded`（`acl.rs:375`）的备份/恢复路径；祖先部分的快照自然停止产生 |
| 新 SID 是否需要账本 | **不需要** | 确定性派生（§1.2），路径即身份 |

### 4.4 用户已有的 ACE 怎么处理

**对齐 codex：保留不撤。** 依据：
- codex 的 `revoke_ace` 调用点只有三处：`deny_read_state.rs:68`、`deny_read_acl.rs:84`、
  `windows-sandbox-service/src/package_lifecycle/cleanup.rs:96`（卸载清理），
  **正常的 workspace-write 路径从不撤销写 ACE**。
- `docs/15:30` 已判定「卸载不撤 ACL」在新模型下仍成立。

具体：
- 旧 AppContainer SID（`S-1-15-2-…`）留下的工作区 ACE：**保留，不主动清**。容器 profile 删掉后这些 ACE
  指向的 SID 已无人持有，属惰性残留，不产生授权效果。
- 祖先链上的 `(RA,S)`：**保留**，同样惰性。不主动撤的理由是撤要遍历祖先、且可能撞权限；
  一次性清理留作可选的维护命令（不在本方案范围）。
- 首次运行**不做自愈式重写**：新机制只补「工作区写 ACE」，命中即跳过（`ScopeGrant::AlreadyPresent`，
  `mod.rs:341`）。用户手工改过 DACL 的情况由「按真实 DACL 探测」兜底（`mod.rs:373-375`）。

### 4.5 卸载生命周期

`shutdown()`（`mod.rs:833`）与安装器只保留两件事：
1. 撤销**本进程**为 MCP 临时根加的写 ACE（`release_all_mcp_containers` 改造后）。
2. 不再删 AppContainer profile（`appcontainer.rs` 已删），不再恢复设备 ACL。

## 6. 风险与测试防线

**R1 · 写约束失效（最高危）**——令牌构造成功但 `WRITE_RESTRICTED` 没生效 / restricting 列表为空，
子进程退化成普通用户令牌。
可能路径：(a) 忘记加 flag（现状就是 flags=0，`windows_impl.rs:179`）；(b) 列表为空仍调用；
(c) 失败后 fallback 到无沙箱 spawn。
防线：单测断言 flags 含 `WRITE_RESTRICTED`、列表长度 ≥ 3；`CreateRestrictedToken` 失败直接返回错误、
不降级（照 codex `token.rs:473-475`、`:512-514`）；真机 `sandbox_denies_write_outside_workspace`。

**R2 · 默认 DACL 未处理 → 匿名管道/新建对象失败**——父进程 `CreatePipe` 出来的 stdio 管道拿不到
restricting SID 的 allow ACE，命令直接起不来。防线：真机 `sandbox_probe` 的
`write_restricted_*` 用例 + 单测断言 default DACL 里出现 logon SID 的 allow ACE。
注意它**不覆盖** libuv 的命名管道（§10.7 已证），不要把它当 `spawn EPERM` 的防线。

**R3 · ACE 漏写或继承断裂**——工作区根是 `SE_DACL_PROTECTED`、owner 是别人、或路径未规范化导致写到了
另一个 SID 上。表现为「区内写也失败」。
防线：写前探测「exact ACE 是否存在」（复用 `has_explicit_grant`，`acl.rs:998`）；
失败时明确报「哪条路径、哪个 SID、什么错误」（现有 `ScopeGrant::Denied`，`mod.rs:342-346`）；
真机用「受保护 DACL 的目录」做一次反例。

**R4 · 删除权口径变化**——我们保留 `FILE_DELETE_CHILD`（`acl.rs:98`），比 codex 宽。
若将来有人为了「更安全」把这位移除，会出现 `rm -rf` 删不动文件的回归。
防线：新增真机用例「区内建 readonly 属性文件并删除」，锁住当前口径。

**R5 · 通过重解析点（junction/symlink）写出工作区**——工作区内建 junction 指向 `C:\Users\…`，
再往里写。**【推断（未验证）】** 写穿透走目标对象的 DACL，工作区 SID 在目标上没有 ACE，
pass-2 应当拒绝。验证方法：真机建 junction 后写目标文件，断言失败；连续两轮。
若不成立，退路是加「拒绝在工作区内创建重解析点」的检查（本仓已有 `add_node_symlink_flags`，
`mod.rs:1343`，说明链接面是已知面）。

**R6 · 读隔离消失带来的信息面**——命令可读 `data_root` 下配置、日志、凭据（若明文存放）。
这是用户已接受的交换，**不缓解**，但必须在 `docs/11-使用指南` 与本文件同时写明，
避免「以为还有读隔离」。防线：只做文档一致性，不做代码。

**R7 · 机制切换期「什么都跑不起来」**——用户的兜底要求。
防线：B 期起保留 `sandbox.os = "app_container"` 一键回退（§4.1），且状态条显示当前后端名；
回退路径本身必须有真机用例（§7 步骤 5 的 (e)）。

**R8 · 验证污染**——今天两次事故的根因：测试在含他人未提交改动的树上跑绿。
防线：每条真机验收前 `git status --porcelain` 必须干净（或明确记录残留文件并排除影响），
证据目录里附 `git rev-parse HEAD` 与 `git status` 输出。

## 7. 工作量拆分（每步含真机验收）

### 为什么分三期而不是一次删完

用户新增的硬要求是「保留一键切回旧机制的配置项，直到新机制在真机上连续验过」。
一次性删掉 AppContainer = 回退开关无处可退。所以：

- **A 期（步骤 1-2）**：新机制与新开关**并存**，默认仍是旧机制。任何一步真机不过，用户无感。

## 10. 第二期：默认档切到「只约束写」（2026-11-12）

> 用户裁定：**不要比参考项目严**。codex / dsh 在 Windows 上都是受限令牌、只约束写、
> 不隔离读；本仓之前默认 AppContainer 读隔离，属于「更严」，本期把默认档换过来。

### 10.1 三档与默认

| 档位 | 行为 | 如何选中 |
|---|---|---|
| `restricted_token`（默认） | `WRITE_RESTRICTED` 受限令牌；写按路径授权，读与网络不约束 | 不写任何配置即默认 |
| `app_container` | AppContainer 读/写都按路径授权（第一期的严格档） | `os = "app_container"` + `os_explicit = true` |
| `logical` | 无 OS 级隔离，只有工具层校验 | 显式配置（仍需 `os_explicit = true`） |

`SHANIU_SANDBOX_OS` 环境变量与 `restricted_token_enabled()` / `use_restricted_token()`
已删除：**默认档不需要任何环境变量**，分发只看每次请求的 `request.os`（`OS_MODE`
原子值为进程内缓存，仅作默认来源），避免并发执行互相污染。

**不对称（2026-11-12 曾有意保留，2026-11-13 已取消）**：第二期只把一次性命令切到默认档，
交互终端与 MCP server 暂留 AppContainer，祖先 ACE 预置条件写成 `os != Logical`。
用户随后裁定「终端也对齐、MCP 也对齐」，三面统一走默认档，详见 §10.8。

### 10.2 老配置迁移（裁决点）

旧版本写出的 `os = "app_container"` 分不清「用户主动选的」还是「旧默认值」。处理：

1. 新增 `sandbox.os_explicit: bool`（`serde(default = false)`），只有它才能表达「用户定过」；
2. `!os_explicit && os == AppContainer` → 视为旧默认值，**一次性迁移**为
   `restricted_token`：先备份 `config.toml.bak-<ms>`，再写回并打 WARN；
3. `os_explicit = true` 的 AppContainer **原样保留**，不迁移；
4. 写回失败不阻断启动：本次按 `restricted_token` 运行，下次启动重试（幂等）。

选择理由：迁移方向是**放宽**（读不再受限），与用户裁定一致；但放宽必须可见可回退，
所以备份 + WARN + 显式标记三件事都做。想留在 AppContainer 的老用户只需在
`config.toml` 的 `[sandbox]` 里写 `os_explicit = true`，其余不动。

真机证据（旧根启动一次）：

```

（只约束写；要留在 AppContainer 请写 os_explicit = true，原文件已备份）
backup=...\legacy-data-root\config.toml.bak-1794493989335
```

迁移后 `config.toml` 为 `os = "restricted_token"`、`os_explicit = true`，
`sandbox_status` 返回 `restricted_token` / `enforcement=full`。

### 10.6 授权账本与撤销（第二期 B）

账本沿用 `sandbox/ancestor-ace.jsonl`，每行含
`(path, sid, mask, kind, existed_before, added_at_ms)`。

`acl::revoke_from_ledger(ledger)` 的语义：

- 只处理 `existed_before == false`（我们独创的 ACE），别人原有的不碰；
- 按 `(path, sid)` 去重，重复记录只撤一次；
- 路径已不存在 → 记 `missing` 并继续，不报错；
- 用 `REVOKE_ACCESS` **精确删除该 trustee 的 ACE**，不做 DACL 快照还原
  （快照会把同期别人的合法改动一起回滚，codex 也不这么做）；
- 幂等：二次调用返回 `unchanged`，DACL 不再变化。

用例 `revoke_from_ledger_is_precise_idempotent_and_tolerates_missing_paths`
覆盖：两条记录（一条 `existed_before=true` 不撤、一条路径已删 → `missing`）、
DACL 复原、二次调用 `unchanged=1`、账本缺失返回默认值。
卸载 hook 与 `docs/15` 的完整卸载流程**本期不接**。

### 10.7 已知限制：node 管道子进程 EPERM

默认档下 `node -e "execSync(...)"` 报
`EPERM: spawnSync C:\WINDOWS\system32\cmd.exe`（退出码 1），影响 npm/pnpm 这类
「用管道 stdio 再 spawn」的工具链。已做的对照（同一受限令牌、同一数据根）：

| 实验 | 结果 |
|---|---|
| `node -e` 直接写文件（区内/区外） | 正常，区外被拒（写约束本身没问题） |
| `spawnSync('cmd', ['/c','echo ok'], { stdio: 'inherit' })` | 成功（`INHERIT_STATUS=0`） |
| `cmd /C "echo piped-ok \| findstr piped-ok"` | 成功（cmd 自己建匿名管道没问题） |
| `powershell -NoProfile -Command "'ps-ok'"` | 成功 |
| `python -c "subprocess.check_output(...)"` | 成功（`PY=ok`） |
| node `spawnSync` / `execSync`（默认管道） | **EPERM** |

#### 10.7.1 失败对象（2026-11-13 令牌级实测）

`EPERM` 不能反推被拒对象：libuv 把这段路径的 Win32 错误直接返回，
`uv_translate_sys_error(ERROR_ACCESS_DENIED)` = `UV_EPERM`（libuv 1.52.1 `src/win/error.c:158`），
所以 node 看到的是 `EPERM` 而不是 `EACCES`。本机没装 Process Monitor，改用等价手段：在与
`windows_impl.rs:205-245` 同形状的令牌下，由探针进程按 libuv `src/win/pipe.c:209-345` 的顺序
逐条调用并记录 `GetLastError`（`docs/evidence/2026-11-13/pipe-eprem-probe/`）。

| 调用（libuv 顺序） | 结果 |
|---|---|
| `CreateNamedPipeA(name, ..., NULL security attributes)` | **成功** |
| `CreateFileA(name, client_access, ...)`（管道客户端） | **拒绝，Win32 5（`ERROR_ACCESS_DENIED`）** |
| `ConnectNamedPipe` / `CreateProcessW` | 未被走到；同令牌下进程创建与匿名管道 stdio 均正常（上表与 `drive-run5/6.log`） |

被拒的是**命名管道客户端的写打开**，不是 `CreateProcessW`。按权限位拆分（同一管道逐项重开）：
`GENERIC_READ` 与 `FILE_READ_ATTRIBUTES` 成功，`GENERIC_WRITE` 与 `WRITE_DAC` 都是错误 5。

机制：命名管道（`lpSecurityAttributes == NULL`）的 DACL 取自 **Win32 命名管道默认 SD 模板**，
不读令牌 default DACL。下表前四种 default DACL 形状下实测该 DACL 逐字节相同：

```
D:(A;;FA;;;SY)(A;;FA;;;BA)(A;;FA;;;S-1-5-21-3226398052-62638092-3539548929-1001)(A;;FR;;;WD)(A;;FR;;;AN)
```

即 SYSTEM / Administrators / 创建者本人全权，Everyone / Anonymous 只读。受限令牌的**写**检查只认
restricting SID，列表里的 Everyone 在这份 DACL 中只有 `FR`，于是读打开放行、写打开被拒。

#### 10.7.2 改 default DACL 为什么修不到（推翻旧结论）

2026-11-13 用五种 default DACL 形状各跑一遍（`run-*.log`）：

| default DACL 形状 | node `execSync` | 管道客户端写打开 | 匿名管道 `CreatePipe` |
|---|---|---|---|
| 继承用户默认 DACL（dsh 注释描述的起点） | EPERM | 拒绝(5) | 拒绝(5) |
| 本仓现状（logon 全权 + OWNER RIGHTS 读控制，替换式） | EPERM | 拒绝(5) | 成功 |
| 本仓现状 + 写 SID `FILE_ALL_ACCESS` | EPERM | 拒绝(5) | 成功 |
| dsh 形状（继承后合并写 SID `FILE_ALL_ACCESS`） | EPERM | 拒绝(5) | 成功 |
| 诊断：令牌 owner 改成写 SID | EPERM | 拒绝(5) | 成功 |

最后一行不是「同类改法」：`SetTokenInformation(TokenOwner)` 直接返回 **1307
(`ERROR_PRIVILEGE_NOT_HELD`)**，需要 `SeRestorePrivilege`，本档不额外加特权，此路不可用。

**旧结论错在两处**：

1. 「管道的 SD 不走令牌 default DACL」对**命名管道**成立，但旧文紧接着把它当成「线上写约束
   机制是否遗漏」的问题，方向错了——default DACL 是**匿名管道/事件/互斥量**等新建对象的来源，
   对命名管道根本没有作用面，补写 SID 是 placebo；
2. 「dsh 撞过同一问题，处理方式一致：不修」与 dsh 源码不符（见下），且旧文没有区分 dsh 的
   注释描述的是**匿名管道**、其 README 才是对命名管道的最终结论。

#### 10.7.3 参考项目各自怎么做

- **dsh**：`src/dsh/packages/sandbox/sandbox-windows-acl/src/token.ts:96-145` 确实实现了
  default DACL 合并（在继承的 existing DACL 上 `SetEntriesInAclW` 一条 restricting SID 的
  `FILE_ALL_ACCESS`），调用点在 `src/index.ts:304`，按
  `tempWriteSid ?? writeSid ?? worldSid` 选 SID；注释里「新建匿名管道（子进程 stdio）第二次
  访问检查失败」的描述针对的是**匿名管道**，与上表一致。
  但 dsh 的 `README.zh.md:188`（同 `README.md:186`）把命名管道这条路径明确登记为
  **不可用**：「libuv 的管道 stdio 用的是 NAMED pipe，其 client 端打开所请求的写访问没有任何
  restricting SID 被授予（是 Win32 层的默认 SD 模板，而非令牌默认 DACL），因此受限进程内
  `spawn(..., { stdio: 'pipe' })` 以 EPERM 失败；继承与忽略 stdio 的 spawn 可用，匿名管道……
  可用」。也就是说 dsh 是「修匿名管道、把命名管道登记为限制」，不是「不修」。
- **codex**：任务给定的参考是 `codex-rs/windows-sandbox-rs/src/token.rs:56-62`，`set_default_dacl`
  为 logon 全权 + OWNER RIGHTS（与本仓现状同形）。**本机没有 codex 源码**（`codex-rs` 目录不存在），
  这一条无法核对行号与它是否也登记了该限制，只能按给定口径转述，不作为实测依据。

#### 10.7.4 我们这次改了什么

**代码行为未改**：`set_default_dacl` 仍是 logon 全权 + OWNER RIGHTS（替换式）。原因：

- 上表证明「按 dsh 形状合并写 SID」对本路径无效，land 了也只是 placebo；2026-11-12 的真机
  `drive-final.log` 已经验过一次同样无效，本轮从令牌层把原因补全；
- 本仓现状不退化：匿名管道 DACL 里有 logon（restricting）全权，`CreatePipe` stdio 正常；
  若改成「继承后合并」也不会多出任何本仓依赖的能力（本仓的 stdio 管道都由父进程 `CreatePipe`
  后继承句柄，不需要孙进程自建命名管道）。

只做了两件事：把 `set_default_dacl` 的注释从「真机未解」补成带根因的说明，并改写本节。

#### 10.7.5 影响与可选项

**影响**：npm/pnpm 脚本、前端构建工具在受限档跑不动（它们靠管道 stdio 再 spawn 子进程）。
工具链本体本身能跑：同一受限令牌下 `pnpm.exe --version` 输出 `12.16.1`
（`pipe-eprem-probe/run-pnpm-exe.log`），失败只发生在它用 libuv 管道派生孙进程的那一步。
为了让模型看清失败原因而不是去猜沙箱坏了，这类失败的工具结果会在 `[sandbox]` 行追加
`denied=piped-stdio`（只在写约束档命中，见 `sandbox::execution_note`）。

可选项（按推荐顺序）：

1. **维持现状，登记为平台限制**（当前选择）：与 dsh 的最终口径一致；写边界与既有权衡不变。
   需要跑 npm/pnpm 脚本时走用户批准的升权。
2. **换写约束机制**（例如 AppContainer/lowbox 或 deny-ACE 模型）：理论上绕开「restricted token +
   命名管道默认 SD」的组合，但这是第二期级别的重构，**本仓没有任何实测**说它能跑通 node 管道
   （`drive-appcontainer.log` 当时因 PATH 里没有 node 连对照都没做成），不能当作已可用方案。
3. **包装工具链**（强制 `stdio:'inherit'` 的 shim）：会丢输出捕获，且改变子进程语义，
   与「工具输出可观测」冲突，不建议。

## 11. 第三期：三面统一走默认档（2026-11-13）

用户裁定（两笔，后一笔覆盖前一笔中「终端保持 AppContainer」的部分）：

1. 「MCP server 进程要对齐参考项目，改走默认的写约束档；终端保持现在的 AppContainer 不动」；
2. 「追加裁定：**终端也对齐**」——exec、交互终端、MCP server 三个命令执行面统一走
   `restricted_token`，AppContainer 只作为可选档保留，不再承担其中任何一个的默认路径。

理由都是同一条：**不要比参考项目严**。上一期「终端/MCP 保持容器」是本仓比 codex/dsh 更严的地方。

### 11.1 三面共用的写范围

`grant_write_scope(workspace_root)` 是 exec / 终端 / MCP 唯一的写 SID 来源：

- 派生「工作区写 SID `S-1-4-x-y`」与「temp 写 SID `S-1-4-x-y-1`」；
- 给 `acl::write_scope(workspace_root)` 的每个位置补持久、可继承的 allow ACE；
- 返回值顺序固定 `[工作区, temp]`，就是受限令牌 restricting 列表里允许写的两个 SID。

MCP 面向每个 server 再补两处：

- `workspace_access = "write"` 的 cwd / `allowed_roots` 每个可写根各派生一个写 SID（同一派生函数），
  读根**不补 ACE**——本档读本来无边界，补了也拦不住读，只会多刷 DACL；
- `TEMP`/`TMP` 改指 `<data_root>/sandbox/mcp-temp/<id>` 并给该目录授权，请求仍先过数据根闸门
  （`guarded_mcp_user_roots`），配置换个键不能绕过「不许摸会话档案」。

契约：`StdioRequest` 新增 `os: OsSandbox`（与 `SpawnRequest.os`、`TerminalRequest.os` 一致），
`prepare_stdio` 按 `request.os` 三分支分发；`ToolContext` 新增 `os: Option<OsSandbox>`，
`unified_exec` 与 `terminal` 用 `ctx.os.unwrap_or_else(current_os_mode)`。全局 `OS_MODE`
**只决定默认来源**，不再有「某条路径偷偷读全局」的分支。

### 11.2 祖先 ACE 的触发条件（按新分工重新核对）

`lib.rs` 启动时的预置条件从 `os != Logical` 收紧为 `os == AppContainer`。
核对结论（逐处确认，不留两边都不管的窗口）：

| 位置 | 判据 | 现在是否可能等祖先权限 |
|---|---|---|
| 启动预置 `provision_ancestors_in_background` | `mode == WorkspaceWrite && os == AppContainer` | 否：默认档不预置 |
| 工具自报 `execution_note` 的 `ancestors=` | `os == AppContainer` | 否 |
| 失败解释 `ancestor_hint` | `os == AppContainer` | 否 |
| `sandbox_status` 的 `ancestor` 字段 | 仅 `(AppContainer, WorkspaceWrite)` 取真实状态，其余 `idle` | 否 |

三面都改成默认档之后，只有显式 `os = "app_container"` 才会起容器，也才需要祖先 ACE；
`logical` 回退与默认档都没有容器，预置了反而是白写 DACL。

### 11.3 交互终端与 exec 的差异（真机逐条）

同一份受限令牌、同一套写 SID、同样挂 Job，差别只在 I/O 层：

| 维度 | `unified_exec` | 交互终端（`terminal`） |
|---|---|---|
| 进程模型 | `CreateProcessAsUserW` + 三根匿名管道 + `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` 句柄白名单 | ConPTY：`CreatePseudoConsole` + `PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE`，管道端不可继承 |
| 输入 | 无 stdin（`NUL`/关闭） | 父进程写 ConPTY 输入管道，逐次 `write` |
| 输出 | 读线程按行回传 `StdioEvent::Line` | 原始 VT 字节流，含 `\x1b[...` 光标/清屏序列，**未做行切分** |
| 编码 | 严格 UTF-8 合法性优先；仅出现非法字节时回退 `GetOEMCP`，且只有回退时才附 `oem-<cp>` | 未解码，原样字节；真机输出里中文以 UTF-8/代码页原样透传 |
| Ctrl+C | 不传（一次性命令，超时/取消走 kill Job） | 不做 `GenerateConsoleCtrlEvent` 注入；按 `\x03` 写入 ConPTY 由 shell 自行解释 |
| 退出判据 | 等进程退出码 | `exit` 后 shell 退出，`read` 会显示 `已退出 · exit=0`；**输出管道要等 `ClosePseudoConsole` 才 EOF**，不能拿读端 EOF 当退出判据 |
| 回收 | 子进程退出即结束 | Job `KILL_ON_JOB_CLOSE` + `close` 关闭 ConPTY，整树回收 |

真机结果（默认档，`enforcement=full`）：能开（返回 `term-<ULID>` 与 cwd）、能敲命令
（`echo TERM-REAL-OK` 输出原样回来）、能写工作区（`echo term> term-out.txt` 后目录里出现该文件）、
能正常退出（`exit=0`，`close` 报「整棵进程树已回收」）。Ctrl+C 注入未做，属未验证项而非绿灯。

### 11.6 已知限制（沿用 §10.7，并区分两种 EPERM）

- **node 管道起子进程**：`spawnSync`/`execSync`（默认管道 stdio）在受限令牌下报
  `EPERM: spawnSync …`。若某个 MCP server 启动时要靠管道 spawn 子进程，表现就是**起不来**；
  这是 §10.7 的限制，不放宽授权去凑。
- **node 写被拒也是 EPERM**：本次真机里 `fs.writeFile` 被 OS 拒绝同样映射成
  `EPERM: operation not permitted, open '…'`。两者 syscall 不同（`spawn` vs `open`），
  排查时看报错里的操作名即可区分。
- 本次选用的 `server-filesystem` 只做 `fs` 读写、不 spawn 子进程，所以默认档下能正常启动；
  这条不能外推成「所有 node MCP server 都能起」。
