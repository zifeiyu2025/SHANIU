## 一、结论先行

> **[2026-11-12 裁定标注]** 逐条状态见 §0.1：第 1、3 条失效；第 2、5、6 条待重算；
> 第 4、7 条仍成立。以下正文保留原样。

1. **形态选型：NSIS，`installMode = "perMachine"`，只出 x64。**
   理由：Tauri 原生支持 NSIS 的四个安装/卸载 hook；perMachine 提供安装期一次提权，
   才能写 `C:\Users`；MSI 的自定义动作要走 WiX fragment/template，卸载阶段更容易踩
   deferred custom action 与回滚语义，当前收益不足以抵消复杂度。详见 §四。

2. **SID 跨机一致性：结论是「推断一致（未验证）」。**
   `DeriveAppContainerSidFromAppContainerName` 只接收名字（`src-tauri/src/sandbox/appcontainer.rs:255-260`），
   本机输出 `S-1-15-2-1983691489-4147020651-3927463519-3530369433-875054126-3321602352-1494959735`，
   结构上不含机器 SID（`S-1-5-21-…`）。但单机无法证明跨机一致，Microsoft 的该 API 文档
   也没有写「跨机一致」这一句（本轮已查原文）。验证方法见 §三。
   **关键：本设计不依赖这个未验证假设**——安装器在目标机上现场派生 SID 再写 ACE，
   不硬编码、不在构建期预计算。

3. **安装期只预置一条权限：`C:\Users` 上的 `(RA,S)`，不继承。**
   这是祖先链里唯一普通用户没有 `WRITE_DAC` 的固定层级（`src-tauri/src/sandbox/acl.rs:1439`）。
   盘根不写；`C:\Users\<user>`、`AppData`、`%TEMP%` 由首次运行的后台预置补（用户可写，
   不需要提权）。安装器不能假装替「未来用户」预置，这条边界如实写进 §五。

4. **卸载按 codex 语义：不撤用户工作区与祖先目录上的任何 ACE。**
   只清我们独占的容器身份（当前用户的 `Shaniu.Sandbox.v1` 与 `shaniu.mcp.*` profile）。
   不做按 SID 定向撤销、不做快照还原、不加命名互斥、不单独造清理守护程序。
   残留 ACE 会显示为「未知账户」，不生效、不影响其它程序；这是对齐 codex 的直接结果，
   不是漏做。详见 §六。

5. **孤儿权限条目：启动时只探测已知路径，设置页提示、用户手动清理；不自动清、不弹窗。**
   判据是「账本/审计里记录过的 SID 已无法解析为已存在身份」，且该 SID 不在当前活跃
   profile 集合里（避免把「本进程刚删过 profile」误报成孤儿）。清理只删该 SID 的显式
   ACE，不动继承、不动其它主体；耗时按现有后台预置那套放到后台。详见 §七。

6. **持久账本（`sandbox/ancestor-ace.jsonl`）保留，理由有两个：孤儿检测需要知道
   「哪些路径、哪些 SID 该探」，以及审计。** 卸载仍然不读它。
   若要删，现有 `acl-audit.jsonl` 只是操作流水，无法可靠反查「当前仍有哪些我们加的
   ACE、分别属于哪个 SID」，孤儿检测会失去探针清单。详见 §八。

7. **数据迁移：安装器不搬数据；安装版使用新的安装模式数据根。**
   首次运行按既有 `data-root` 记录发现旧便携目录，提供「复制导入（不移动、可回滚）」。
   不做自动切换，不覆盖、不删除原便携目录。详见 §九。

## 三、SID 是否跨机确定性

> **[2026-11-12 裁定标注 · 待重算，可能整体失效]** 本节前提是 AppContainer profile。
> 若迁移后改用受限令牌、不再创建 AppContainer profile，则「SID 跨机一致性」失去对象；
> 若仍用 AppContainer 但只授予工作区写权限，则它只剩「写权限授给谁」这一个用途，
> 需重新做成本收益评估。跨机验证本身可以暂缓，等迁移方案定稿。

### 3.1 代码事实

- 生产 profile 名是常量：`Shaniu.Sandbox.v1`（`src-tauri/src/sandbox/appcontainer.rs:28`）。
- SID 派生只调用 `DeriveAppContainerSidFromAppContainerName(PCWSTR(name))`，
  入参只有名字（`src-tauri/src/sandbox/appcontainer.rs:255-260`）。
- 派生结果用于 ACL trustee；profile 不存在也能派生（`derived_sid` 明确「只派生、不创建」，
  `src-tauri/src/sandbox/appcontainer.rs:168-174`）。

### 3.2 结论与依据

- **结论：推断跨机一致（未验证）。**
- 支持「一致」的依据：
  1. API 只接收名字，没有机器标识、用户 SID 或安装路径入参（代码事实）。
  2. 本机输出是 `S-1-15-2-…`（AppContainer 权威），不是 `S-1-5-21-<机器 SID>-…`；
     机器 SID 没有被嵌进去（本机实测输出）。
  3. 同一台机器上，profile 删除后重建仍得到同一 SID（代码注释 `appcontainer.rs:27`
     「容器 SID 由名字决定，重启后仍是同一个 SID」；本机同进程多次派生结果一致）。
- 不能当成事实的原因：
  1. 本机只有一台机器、一个用户，无法比对第二台机器。
  2. Microsoft 的 `DeriveAppContainerSidFromAppContainerName` 文档只写「Gets the SID of
     the specified profile」，**没有**承诺跨机一致（本轮已抓取原文核对）。
  3. 具体哈希算法（是否含大小写归一、是否加盐）没有官方文档依据，属推断。

### 3.3 验证方法（必须做，成本约 0.5 天）

1. 在第二台 Windows 机器或干净 VM 上，用同一个 API 派生 `Shaniu.Sandbox.v1`，比对完整
   SID 字符串是否等于本机值。
2. 在第二台机器上先按该 SID 给一个临时目录写 ACE，再创建 profile，确认 `icacls` 显示的
   身份与 ACE 命中一致（验证「先写 ACE、后建 profile」的顺序可行）。
3. 至少覆盖一个 Win10 与一个 Win11 版本，记录系统版本号；不一致就立即停用
   「安装期预置」路线，退回「首次运行一次性提权」（codex 的 first-run 形状）。

### 3.4 为什么本设计不被这个假设卡住

- 安装器在**目标机**上现场调用派生，拿到的就是该机器上运行期会用的 SID；不跨机传递、
  不硬编码。
- 卸载不按 SID 反查撤销（§六），所以卸载也不依赖跨机一致性。
- 只有「构建期把 SID 写死进安装脚本」才会被这个假设卡住；本方案明确不做。

## 四、安装器形态选型

> **[2026-11-12 裁定标注 · 部分成立]** NSIS 作为安装器形态仍可选；但
> 「perMachine 是为了提权写 `C:\Users`」的理由失效。安装器若保留，理由改为
> 「正常安装/卸载、快捷方式、升级体验」；perMachine 与 perUser 需要重新权衡
> （不再有必须写系统级 ACL 的硬约束）。

### 4.1 候选对比

| 维度 | NSIS | MSI（WiX） |
|---|---|---|
| Tauri 支持 | 默认；`bundle.windows.nsis` | `bundle.windows.wix` |
| 安装期提权 | `installMode: "perMachine"` 需要管理员 | MSI 本身就是 per-machine |
| 扩展点 | `installerHooks`：`NSIS_HOOK_PREINSTALL/POSTINSTALL/PREUNINSTALL/POSTUNINSTALL`（已核对 Tauri 文档） | WiX fragment / 自定义 template；deferred custom action |
| 静默安装 | `/S` | `msiexec /qn` |
| 修复 | 无 repair 概念 | 有 Repair |
| 卸载钩子 | PREUNINSTALL 阶段执行脚本（顺序需在生成的 `.nsi` 里复核） | InstallExecuteSequence 自定义动作（需处理回滚/ impersonation） |
| 构建工具链 | NSIS 由 Tauri 自带/下载 | 需要 WiX 工具链 |
| 适合本需求 | 高：一次提权 + 两个短动作 | 低：ACL 与 profile 清理都不需要 MSI 的事务语义 |

### 4.2 结论

> **[2026-11-12 裁定标注 · 部分失效]** 「per-machine 是为了提权写 `C:\Users`」这个前提
> 随 §五 一起失效；「选 NSIS」的形态结论仍成立（hook 能力、静默参数、卸载载体不变），
> 但 `installMode` 要在 perMachine / perUser 之间重新权衡——不再有「必须一次提权写系统
> 级 ACL」的硬约束。下方 per-machine / per-user 论证保留原文，按旧需求记录。

**选 NSIS + `perMachine`。** 具体理由：

1. 我们只需要两个短动作：安装后写一条 `C:\Users` ACE；卸载前删当前用户的容器 profile。
   NSIS hook 足够，且能直接调用我们自己的可执行文件，不必在 NSIS 脚本里重写 ACL 逻辑。
2. MSI 的 Repair 对我们没有额外价值：运行期每次启动都按真实 DACL 探测并补缺
   （`src-tauri/src/sandbox/acl.rs:1476-1493`），天然自愈；ACL 不靠 MSI 修复。
3. MSI 卸载自定义动作要处理 deferred/impersonation/rollback，写错会留下半完成状态；
   NSIS 的 PREUNINSTALL 是顺序脚本，失败可记录后继续，符合「失败不阻断卸载」。

**per-machine vs per-user：**

- 选 per-machine：安装期需要管理员，才能写 `C:\Users`；这是需求 1（一次性准备权限）的前提。
- 代价如实写清：**非管理员用户不能自己安装**；安装时有一次 UAC；程序装到
  `%ProgramFiles%\SHANIU`，用户数据仍在各自 `%APPDATA%`/`%LOCALAPPDATA%`。
- 不选 per-user：per-user 安装无法写 `C:\Users`，只能退回首次运行提权，等于把需求 1
  的「安装时准备」变成「首次使用时弹 UAC」，与目标相反。
- 不选 `both`：两种模式会让「有没有预置 `C:\Users`」变成运行期分支，验收矩阵翻倍；
  v1 只做 per-machine。

### 4.3 升级 / 修复 / 静默 / 卸载

> **[2026-11-12 裁定标注 · 部分失效]** 「升级时 POSTINSTALL 预置幂等」「修复靠运行期
> 补 ACL」两条以安装期预置为前提，随 §五 失效；「静默 `/S`」「`PREUNINSTALL` 调主程序
> 早期分支」这两个载体形态仍成立。卸载动作的具体内容（删 profile）待新模型重算（§6.2）。

- 升级：NSIS 覆盖安装；`POSTINSTALL` 的预置是幂等的（先探测，命中 1–2ms 跳过），
  升级不会重复付出写 DACL 的代价。
- 修复：没有 repair 按钮；ACL 缺失由运行期自愈。若用户手动删了 ACE，下次启动补回。
- 静默：`/S`；per-machine 下仍需管理员令牌（由部署方提权，或 UAC 已批准）。
- 卸载钩子：`PREUNINSTALL` 调 `shaniu.exe --uninstall-clean`；不写 `POSTUNINSTALL`
  （卸载后安装目录已被删，不能再依赖其中的二进制）。

### 4.4 代码签名缺失时的 SmartScreen

- NSIS 与 MSI 在未签名时都会触发「Windows 已保护你的电脑 / 未知发布者」；差别不在格式。
- 不能承诺「NSIS 更不容易被拦」。缓解手段只有：后续购买代码签名证书并积累信誉；
  在下载页给出 SHA-256；保留便携 ZIP 作为低摩擦备选。
- 本轮不做签名，不把 SmartScreen 行为写成已解决。

### 4.5 WebView2

- 默认 `downloadBootstrapper` 需要联网；目标机器若无 WebView2 会失败。
- v1 建议 `embedBootstrapper`（安装包略大，仍需要联网下载运行时）；完全离线场景再评估
  `offlineInstaller`（体积约百 MB 级）。这是实现阶段的一个配置项，不影响本轮结论。

## 五、安装期权限预置（只做一条）

> **[2026-11-12 裁定标注 · 失效]** 读隔离下线后不再需要祖先遍历权，
> 「安装期写 `C:\Users`」整体预计取消。本节连同 5.1–5.5 保留作为决策记录，
> 等迁移方案确认后统一删除或改写；**不要再按本节去实现权限预置**。

### 5.1 写什么、为什么只有这一条

祖先链 `ancestor_chain` 会包含 `C:\Users`、`C:\Users\<user>`、`AppData`、`AppData\Local`、
`TEMP` 以及工作区路径（`src-tauri/src/sandbox/acl.rs:175-217`）。其中：

| 层级 | 谁能写 DACL | 安装期处理 |
|---|---|---|
| `C:\Users` | 只有管理员（`acl.rs:1439` 明确「这类系统拥有的层级：需要一次管理员」） | **安装器写** |
| `C:\Users\<user>` / `AppData` / `AppData\Local` / `%TEMP%` | 该用户自己 | 首次运行后台补（现有机制） |
| 盘根 `C:\` / `D:\` | TrustedInstaller/SYSTEM | **不写**（见 5.4） |
| 工作区根 / 工具链目录 | 用户自己 | 运行期按需补（现有机制） |

安装器运行在管理员上下文，但**不知道最终用户是谁**：per-machine 安装可能由 IT 管理员
完成，实际使用者是另一批账号。因此：

- 安装器不可能替「未来用户」写 `C:\Users\<user>`；这条由该用户首次运行时补。
- 安装器也不枚举现有用户去写他们的 profile 目录：那会把安装时间变成
  「每个用户 +几十秒」，而且对未来用户无效；运行期本来就能写，不需要提前做。

### 5.2 具体写法

- 目标：`C:\Users`。
- Trustee：目标机上现场派生的 `Shaniu.Sandbox.v1` SID（不硬编码）。
- 掩码：`FILE_READ_ATTRIBUTES | SYNCHRONIZE` = `0x100080`（`acl.rs:85`）。
- 继承：`ACE_FLAGS(0)`，**不继承**（`acl.rs:1489`）。写成可继承会把 `(RA,S)` 转发进
  所有用户目录，扩大面且会触发整棵子树重算，绝不能做。
- 合并方式：`SetEntriesInAclW` 只增这一条，保留其它 trustee；不做整份 DACL 替换。
- 幂等：先 `has_explicit_grant(dir, sid, mask)` 探测；命中直接返回 `AlreadyPresent`，
  零写入（`acl.rs:1480-1495`）。
- 复用现有代码：安装器只需调用已经公开的
  `sandbox::ensure_ancestor_for(Path::new("C:\\Users"), PROFILE_NAME)`
  （`src-tauri/src/sandbox/mod.rs:491-495`），不新增 ACL 实现。

### 5.3 执行载体

- 建议新增一个仅做生命周期动作的极小子命令，由 NSIS 的 `POSTINSTALL` 同步调用：
  `shaniu.exe --sandbox-preset-machine`。
- 为什么不新增第二个 exe：这是「一次 API 调用」级别的动作，不需要 codex 那种常驻
  setup helper；用主程序早期参数分支即可，避免多一个安装产物与签名对象。
- 该分支必须在 `shaniu_lib::run()` 之前处理并退出（`src-tauri/src/main.rs:1-5`），
  不能初始化 Tauri/WebView。
- 结果落盘：`$INSTDIR\install-acl.log`（一行结果 + 耗时 + SID），NSIS 用退出码判断：
  `0` = written/already present；`2` = denied/failed。
- 失败语义：**记录并继续安装**，不中止。理由与 codex 的初次 provisioning 一致：
  ACL 失败只影响冷工作区里依赖 `metadata` 探测的工具，不应让整个安装回滚；
  安装完成页明确提示「沙箱权限预置未完成，首次运行可能提示需要管理员」。
- 同步而非后台：只有一条 ACE，且必须在使用者启动应用前完成；后台化会让首次运行
  在「预置还没写完」时看到 `C:\Users` 拒绝，状态反而更差。耗时风险见 §十。

### 5.4 盘根不写（对需求前提的纠偏）

需求里提到「盘根级别路径」，但当前代码与文档的口径是：**盘根不需要 ACE**。

- 代码注释：`acl.rs:175-217` 明确「盘根不写」，并称 2026-11-12 实测 `C:\`/`D:\` 全裸
  也能跑通冷构建。
- 但该实测原始输出未入库，`docs/13:11-12` 已把同类探针结论标为「无法核实」，
  `docs/14:260-270` 也有待测项。
- 因此本文的处理是：**安装器 v1 不写盘根**；把「盘根是否需要」列入第一步验收，
  用可复跑脚本（`scratch/evidence-2026-11-12/README.md` 的测法）重新测一次。
  若复测证明需要，再单独加「每盘根一条 ACE」的步骤——它同样需要管理员，但仍不建议
  在没有证据前先写。

### 5.5 与账本的关系

- 安装器写的 `C:\Users` ACE **不写账本**：安装器不知道最终用户的数据根，而且卸载不撤
  这条 ACE（§六），写账本没有直接消费方。它由孤儿检测的「固定路径 + 派生 SID」覆盖
  （§7.2）。
- 运行期账本只记运行期写的层级（`mod.rs:328,533,572,637`）；`C:\Users` 被安装器写成
  `AlreadyPresent` 后，运行期连账本也不会记它。
- 这意味着孤儿检测必须额外维护一个静态路径 `C:\Users`；如果将来要支持「撤销所有我们
  加过的权限」，也需要把这层纳入探针集合（§8.2）。

## 六、卸载生命周期（对齐 codex：不撤用户与祖先 ACL）

> **[2026-11-12 裁定标注 · 部分成立]** 「卸载不撤用户工作区/祖先 ACL」仍成立，
> 且与新模型不冲突。但「删除 AppContainer profile」只在仍使用 AppContainer 时成立；
> 若迁移为受限令牌模型，容器身份的形式会变，6.2 的清理对象需要重写。
> 6.4 的残留描述（未知账户 ACE）同样随 SID 模型重算。

### 6.1 参考项目事实

- codex：命令退出和崩溃都故意不撤工作区 ACL（`scratch/reference-acl-cleanup.md:109-121`，
  原始注释 `deny_read_state.rs:33-42`）；卸载明确「retain all user files, including
  sandbox caches and ACLs」（同文档 `:173`，原始 `uninstall_windows.rs:33`）；
  只清理自己的 home/账号/组/防火墙。
- dsh：workspace ACE 永不撤，且**完全没有卸载清理**（同文档 `:394-401`）。
- ZCode：不写目录 ACL，无卸载清理。

### 6.2 我们的卸载动作（只此一项）

**删除当前用户的容器身份：**

1. `Shaniu.Sandbox.v1`（若存在）。
2. 所有 `shaniu.mcp.*`（复用 `list_mcp_profiles` / `reclaim_orphans`，
   `src-tauri/src/sandbox/appcontainer.rs:202,226`）。
3. profile 不存在、包目录已丢、SID 已无法解析 → 一律算成功（幂等）。
4. 删除失败（例如仍有进程持有）→ 记录原因，继续卸载，不阻断。
5. 其它用户的 profile 不处理：per-machine 安装的卸载者通常只是其中一个用户；
   跨用户清理会越权，且需要枚举 profile，收益低于风险。这是已知边界。

**明确不做：**

- 不撤工作区、祖先目录上的 ACE（`C:\Users`、`C:\Users\<user>`、`AppData`、`TEMP`、
  工作区根、工具链目录）。
- 不做快照还原（会覆盖用户在授权后对 DACL 的其它修改）。
- 不做按 SID 定向 `REVOKE_ACCESS`（没有消费方）。
- 不加命名互斥（安装/卸载/运行期不会同时写同一条 ACL：安装预置只写 `C:\Users` 一次；
  卸载不写 ACL；运行期写入由单实例/现有流程串行）。
- 不新增常驻服务、清理守护程序、独立 setup 二进制。

### 6.3 执行载体与顺序

- `PREUNINSTALL` 调 `shaniu.exe --uninstall-clean`（主程序早期参数分支，不初始化 GUI）。
- 该分支只做 §6.2 的 profile 删除，结果写 `%TEMP%\shaniu-uninstall-clean.log`，
  退出码 `0` = 清理完成/本来就没有；`2` = 有 profile 删除失败（NSIS 记录后继续）。
- 运行中的实例：依赖 Tauri NSIS 模板的「应用正在运行」检查/关闭流程；若仍有进程，
  删除会失败并记录，不阻塞卸载。**hook 的精确插入点需在生成的 `.nsi` 里复核**
  （Tauri 文档定义了 PREUNINSTALL 语义，但模板是生成物，属 [推断]）。
- 应用自身退出时已经在删 profile（`src-tauri/src/sandbox/mod.rs:863-868`），
  所以这个卸载动作主要是**兜住崩溃残留**，不是新的常驻机制。

### 6.4 残留 ACE：如实登记

卸载后盘上会留下指向已删除 profile 的 ACE：

- `C:\Users` 上安装器写的那一条；
- 运行期写入的 `C:\Users\<user>`、`AppData`、`AppData\Local`、`%TEMP%`、工作区根、
  工具链目录、以及账本里记录的各级祖先。

表现：资源管理器/`icacls` 里显示为「未知账户」或 SID 字符串；ACL 不生效、不会给任何
现存身份授权，不影响其它程序。

**已知边界（必须原样保留在用户文档里）：** 从卸载完成到用户下次在设置页点「清理孤儿
权限」之前，这些条目会一直显示为「未知账户」；它们不生效、不影响其它程序，也不是
「权限被提权」的迹象。何时能清、由谁清，见 §七。

注意：应用**每次正常退出**都会删 profile（`mod.rs:863-868`），所以「ACE 指向不存在身份」
在两次运行之间本来就存在；卸载只是把它变成永久状态。重装后同一台机器会派生同一 SID，
这些 ACE 重新生效，不会重复累加（运行期探测命中即跳过）。

### 6.5 与旧文档的关系

- 本文取代 `docs/14:230-246` §六的「按账本精确删除」。
- `scratch/reference-acl-cleanup.md:603-607` 曾建议「工作区那条也清」；用户 2026-11-12
  最终口径推翻了该建议。未来读者以本文为准，不要按那份调研的 6.2 节落地。
- 需要后续同步的代码注释：`src-tauri/src/sandbox/mod.rs:327`（「卸载要能按账本精确删」）。
  该文件在另一条线的未提交改动里，本轮不动。

## 七、孤儿权限条目：检测与手动清理

> **[2026-11-12 裁定标注 · 待重算]** 机制（设置页提示、手动、定向、后台）可以保留，
> 但判据依赖「我们有一个专属 SID，且能判断它不可解析」。若新模型改用受限令牌，
> 授权主体可能不再是 AppContainer SID，甚至不再需要为目标目录写 ACE——
> 那样本节整体失去对象。等迁移方案确定后重写 7.2/7.3 的探针与判据。

### 7.1 问题与可达性

卸载后（以及 MCP profile 被回收后）盘上会留下指向已删除身份的 ACE。系统自带工具不清理
NTFS 权限；第三方「清理优化」工具不知道哪条是我们加的，可能连同用户自己的授权一起删。
所以这件事由我们自己做，但只做**手动、定向、可解释**的清理。

必须先说清可达性，避免把功能写成它做不到的事：

- 卸载完成后本机已经没有应用，**当次卸载不可能弹设置页**。检测发生在下一次启动
  已安装版或便携版时。
- 但下一次启动会**重建同名 profile**，同一台机器派生同一 SID（§三），这些 ACE 会重新
  可解析——所以「刚卸载又马上重装」通常**不会**被报成孤儿，这是正确行为，不是漏检。
- 真正会被报出来的场景：
  1. profile 名升级（例如 `Shaniu.Sandbox.v1` → `v2`），旧 SID 永久不可解析；
  2. MCP server 被移除：启动回收会删掉它的 profile（`mod.rs:1075-1078`），但它在工作区
     `write_scope` 上留下的 ACE 仍在，账本里记的 SID 已不可解析；
  3. 崩溃/手工删除 profile 后的残留；
  4. 用户切换过数据根/工作区，旧工作区上的 scope ACE 仍在。
- 因此 UI 文案不能写「安装残留」，应写「指向已删除沙箱身份的权限条目」。

**必须直说的一处可达性缺口：** 如果你的目标是「卸载后立刻把那个未知账户清掉」，本功能
在应用未安装时没有宿主可弹设置页；重新装回来又会重建同名 profile、同一 SID 恢复有效，
按 SID 解析判据就**不是孤儿**了（这不是漏检，是定义使然）。因此：

- 本功能真正覆盖的是「SID 永久不可解析」的残留（profile 名升级、MCP server 移除、
  崩溃/手工删 profile、旧工作区）。
- 「卸载当场清理」只能由卸载器做，而且必须做成**显式可选、默认关闭**（默认行为仍对齐
  codex：不撤用户/祖先 ACL）。是否加这个可选项，作为 §十二 的第 3 件事交给用户拍板；
  本文按用户当前口径**不默认实现**。

### 7.2 探测范围：只探已知路径

不做全盘扫描。探针集合是以下三类的并集，按 `normalize` 去重、只保留真实存在的目录：

1. **账本里的路径**：`sandbox/ancestor-ace.jsonl` 中 `existed_before = false` 的全部
   `path`（`kind=ancestor` 与 `kind=scope` 都算；`acl.rs:1496-1563`）。
   这是唯一能覆盖「过去写过、现在已不在当前工作区」的清单。
2. **当前 `write_scope` 的路径**：工作区根、`TEMP`/`TMP`/`temp_dir`、
   `CARGO_HOME`/`RUSTUP_HOME`/`PNPM_HOME`/`NPM_CONFIG_PREFIX`、`~/.cargo`、`~/.rustup`
   （`acl.rs:115-160`）。工作区相关的那部分在打开工作区后再补探一次。
3. **安装器固定路径**：`C:\Users`（安装期写入、不在账本里，见 §5.5）。

审计日志 `acl-audit.jsonl` 可作为第四类兜底路径来源（用户提到「账本/审计里记录过的
那几条」），但它是操作流水，可能包含失败项；**以账本为主，审计只补路径，不补 SID 状态**。

耗时：每条是 `GetNamedSecurityInfoW` + 逐 ACE 扫描，1–2ms 级；几十条也在毫秒到几十毫秒。
仍放到后台线程，启动流程不等待；设置页先显示「检测中」，完成后显示结果。

### 7.3 判据：什么叫「孤儿」

对每个已知路径，读取 DACL，只认**显式 ACE**（跳过 `INHERITED_ACE`，与
`acl.rs:1064-1066` 的扫描口径一致），命中以下条件才记为孤儿：

1. ACE 的 trustee SID 属于「我们记录过/已知的 SID 集合」：账本里的 `sid` 字段、
   安装器固定路径对应的当前派生 SID、以及历史 profile 名的派生 SID；
2. 该 SID 不在「当前活跃 SID 集合」里：当前 `Shaniu.Sandbox.v1`、当前配置里每个
   `shaniu.mcp.<id>` 的派生 SID；
3. `LookupAccountSidW(sid)` 返回「无法解析」（预期为 `ERROR_NONE_MAPPED`）。

第 2 条是防误报的关键：应用每次退出都会删 profile（`mod.rs:863-868`），所以两次运行
之间当前 SID 本来就不可解析；如果只按第 3 条判断，每次启动都会把**所有** ACE 报成孤儿。
检测必须在应用运行时（profile 已 ensure）执行，并且仍用派生出的活跃 SID 集合兜底。

`LookupAccountSidW` 对「profile 已删除的 AppContainer SID」返回 `ERROR_NONE_MAPPED`
属 [推断]，实现前用一个小工具验证（建 profile → 写 ACE → 删 profile → 再查）。

另外：账本里 `existed_before = true` 的条目跳过——那条 ACE 不是我们独创的，即使 SID
不可解析也不归我们删。

### 7.4 展示与交互

- 位置：设置页「沙箱权限」区；只在检测到 N ≥ 1 时出现一行提示，不弹窗、不打断启动。
- 文案示例：「检测到 N 条权限指向已删除的沙箱身份。它们不会给任何程序授权，只影响
  权限列表的显示。可以手动清理。」
- 交互：可展开查看路径列表（最多显示前若干条，其余折叠）；一个「清理孤儿权限」按钮；
  清理中显示进度与当前路径；结束后汇总「已清理 X 条，失败 Y 条」。
- 不提供「自动清理」开关；不提供定时任务。

### 7.5 清理实现要求

- **只删该 SID 的显式 ACE，保留所有其它 ACE（包括其它主体的显式 ACE 与所有继承 ACE）**，
  不改 DACL 保护标志。
- **不要直接复用现有 `revoke_ace`**：它用 `REVOKE_ACCESS`（`acl.rs:1211-1258`），
  Win32 语义是「移除该 trustee 的所有 ACE」，无法从代码保证只删显式、不碰继承；
  现有测试只覆盖了「不动其它主体」（`acl.rs:2158`），没有覆盖继承 ACE。
  实现时应新增一个「显式过滤」变体：读 DACL → 复制除「目标 SID 且非
  `INHERITED_ACE`」之外的全部 ACE → `SetNamedSecurityInfoW` 写回。
- 掩码：孤儿 SID 已经不再被任何进程使用，删该 SID 在该路径上的全部显式 ACE 即可；
  不必按掩码细分。若要更保守，可按账本 `mask` 只删对应掩码的 ACE。
- 幂等：ACE 已不在 → 算成功；返回实际删除条数。
- 失败隔离：单条失败不阻断其余；汇总失败路径与 Win32 错误码，写审计日志。
- 账本：追加 `kind = "revoked"`、`reason = "orphan-cleanup"` 的记录（含 path/sid/mask），
  保持追加写；读取方把「同一 path+sid 的后续 revoked」视为已撤销。不要重写整份账本。
- 后台化：与预置一致，走后台线程；UI 只轮询进度，不阻塞。

### 7.6 并发

清理与后台预置可能同时改同一个目录的 DACL。清理只动「不可解析的 SID」，不会影响正在
运行的沙箱，但读-改-写仍可能丢掉另一方的更新。因此：

- 进程内：给所有 DACL 写操作（grant / revoke / cleanup）共用一把写锁；现有
  `AclManager` 是每线程一个实例，不提供跨线程串行化，需要新增一个共享锁。
- 跨进程：不引入 dsh 的 per-path `LockFileEx`。单实例已按数据根限制，多数据根并发是
  现存缺口（交付前在 §十 风险表登记），不在本轮为孤儿清理单独造锁。

### 7.7 与卸载、参考项目的关系

- 卸载语义不变：仍然不撤工作区/祖先 ACE（§六）。
- 孤儿清理是**产品新增能力**，codex 没有对应实现（`scratch/reference-acl-cleanup.md:173`
  明确其卸载保留 ACL）。这不改变卸载行为，只给用户一个手动删除「SID 已不存在」条目的
  入口，避免用户去用不安全的第三方工具。

## 八、持久账本的去留

> **[2026-11-12 裁定标注 · 待重算]** 若不再有祖先/范围授权，账本的「探针清单」
> 用途大幅缩水；保留理由可能只剩审计，或将来记「工作区写授权授予谁」。
> 不删除本节，等新模型确定后再定去留。

### 8.1 现状（代码为准）

- 路径：`<data_root>/sandbox/ancestor-ace.jsonl`（`acl.rs:1496-1500`）。
- 字段：`kind` / `path` / `sid` / `mask` / `inherit` / `existed_before` / `added_at_ms`
  （`acl.rs:1544-1552`）。
- 只在真的写入成功后追加；运行期判断缺不缺**不信账本**，一律按真实 DACL 探测
  （`acl.rs:1508-1511`）。
- 卸载本轮不读它；孤儿检测读它（§七）。

### 8.2 结论：保留，理由有两个（都不是「卸载需要」）

1. **孤儿检测需要探针清单**：要知道「哪些路径、哪些 SID 该探」。账本记录的是成功写入
   的 `path` + `sid` + `mask` + `existed_before`，正好是探测所需的输入；
   `acl-audit.jsonl` 是操作流水，可能包含失败项，且不保证能反推「当前还在不在」，
   不能单独承担这个职责。
2. **审计/排障**：能回答「这台机器上我们到底加过哪些级、属于哪个容器身份」；
   配合孤儿检测结果，能解释「为什么设置页说这条失效了」。

成本：每条 ACE 一行 JSON，追加写；量级是个位数到几十行，可忽略。账本不参与授权判定
（运行期始终按真实 DACL 探测），损坏也不会导致多给或少给权限。

不保留的代价：孤儿检测退化到「全盘/全祖先链扫描」，既慢又无法区分「我们加的」与
「别人加的」；审计也失去状态清单。因此不删。

**安装器写的 `C:\Users` 不在账本里**（§5.5）。孤儿检测用「固定路径 + 当前/历史派生
SID」覆盖它；如果将来要支持「撤销所有我们加过的权限」，需要把这层也纳入探针集合，
本轮不为此新增机器级记录。

## 九、数据迁移（便携版 → 安装版）

> **[2026-11-12 裁定标注 · 仍成立]** 本节与沙箱模型无关；安装器若因体验保留，
> 数据迁移方案照旧有效。若最终不做安装器，本节随安装器一起搁置，但迁移判据仍可复用。

### 9.1 现有解析逻辑

- 安装版：配置 `%APPDATA%\SHANIU`，数据 `%LOCALAPPDATA%\SHANIU`（`config.rs:1459-1478`）。
- 便携版：`<exe 目录>\data`（`config.rs:1448-1453`）。
- 首次判定按 exe 目录 hash 落记录（`config.rs:1536-1547`）；有记录后**永不改判**
  （`config.rs:1617-1660`）。
- 现有「便携目录不可写 → 用户确认后切安装模式」只改记录，**不搬数据**，原目录原样保留
  （`config.rs:1808-1852`）。

### 9.2 方案：不自动迁移，安装版使用新根；首次运行提供复制导入

安装器**不**搬数据：

- per-machine 安装可能由管理员执行，`$PROFILE`/`%LOCALAPPDATA%` 指向的未必是最终用户；
  在安装器里拆分「配置根/数据根」并写入别人的 profile，风险高于收益。
- Tauri NSIS 的「删除应用数据」勾选项针对的是 bundle identifier 目录；我们的数据在
  `SHANIU` 下，不能依赖它做迁移或清理（**需在生成的 `.nsi` 里核对实际路径**，属 [推断]）。

首次运行导入（应用内，按用户、无需提权）：

1. 条件：当前判定为安装模式；安装数据根为空或不存在；`%LOCALAPPDATA%\SHANIU\data-root\`
   下存在 `kind = "portable"` 且 `path` 仍存在的旧记录。
2. 交互：列出候选旧数据目录，默认选中最近一条；用户可「导入」或「跳过」。
3. 导入语义：**复制，不移动**。
   - 配置侧（`config.toml`、`secrets\`、`settings-backup\`）→ `%APPDATA%\SHANIU`；
   - 数据侧（`sessions\`、`rollouts\`、`logs\`、`cache\`、`crash\`、工作区等）→
     `%LOCALAPPDATA%\SHANIU`；
   - 未知文件按原相对路径复制到数据根，避免丢历史。
4. 幂等：成功后写 `%APPDATA%\SHANIU\migration.json`（源路径、时间、版本）；
   有标记就不再自动提示。失败则不写标记，下次可重试；不覆盖已存在的目标文件，
   冲突时给出清单让用户决定。
5. 密钥：`secrets\` 是 DPAPI 密文，**同机同用户**复制后可直接解密；跨机导入需要用户
   重新填写 API Key（这是 DPAPI 的边界，不是迁移缺陷）。
6. 回滚：原便携目录一个字节不动；用户随时可以继续用便携版启动（其记录仍在）。
   安装版卸载后数据仍在 `%APPDATA%`/`%LOCALAPPDATA%`（除非用户主动勾选删除数据）。
7. 没有记录可查（用户删过 `data-root`）：提供「手动选择旧数据目录」入口；
   不做全盘扫描。

### 9.3 明确不做的

- 不在安装器里自动复制。
- 不把便携数据「移动」到新根（移动就没有回滚）。
- 不合并两份非空数据（冲突不可自动判定）。
- 不改 `SHANIU_DATA_DIR` 的语义（仍然优先，且不落记录）。

   路径与账本一致；启动过程无弹窗、无阻塞。
2. 正常运行时（profile 存在、SID 可解析）N = 0，不误报（防「退出即删 profile」误报）。
3. 点清理后：目标路径上该 SID 的**显式** ACE 消失；其它主体的 ACE、继承 ACE、
   DACL 保护标志逐条不变（清理前后 DACL 快照对比）。
4. 再次点清理：返回 0 条，无错误（幂等）。
5. 单条失败（只读/被占用路径）不阻断其余，UI 汇总「成功 X / 失败 Y」并给出日志位置。
6. 全程无自动清理、无定时任务、无弹窗打断；不点按钮就永远不清。
7. 账本出现对应的 `kind=revoked` 记录，审计可追溯。

### 工作量与前置条件

- 合计约 4–5 天：安装器三步约 3–4 天，孤儿检测与手动清理约 0.5–1 天
  （不含代码签名、不含 CI 打包改造）。**这比原定 4 天预算多出约 0.5–1 天**，如实登记。
- 必须准备：一台干净 Win11 VM + 一个非管理员账号；第二台 Win10/11 用于 SID 跨机验证；
  一个可写权限受限的测试目录用于验证清理失败隔离。
- 本机写 DACL 的耗时决定第 1 步是否要加安装页提示；没有实测前不对外承诺「安装很快」。
