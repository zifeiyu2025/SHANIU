## 三件专项的专项证据

### 专项一：断流不再当成功 —— 本轮触发 0 次，代价为 0

- 171 次模型请求：`[req] ... end ok` 171，`end err` 0，`end TIMEOUT` 0。
- 10 份档案的 `turn_end.error` 全为 `null`，即**没有任何一题以 `failed` 收口**：
  `reason=Completed` 6 题、`reason=BudgetExhausted` 4 题、`reason=Failed` **0 题**。
- 全会话 grep `VERIFY_FAILED` / `宿主验证未通过` / `完成标记` / `EMPTY_RESPONSE` / `INCOMPLETE` /
  `CONTENT_FILTERED` 只命中源码与文档正文，没有一条是运行时事件。

结论：本轮端点每次都发了终态标记，新收紧行为**没有拦下任何回合**，因此
「模型真的失败」与「端点没发终态」两类计数都是 **0**。这条收紧在本轮是纯安全增益，没有可观测代价；
代价只有在端点偶发不发终态时才会出现，本轮样本覆盖不到，不做能力推断。

### 专项二：预算耗尽不再丢最后一次工具调用 —— 已直接证实生效

同一题 `repo-feat-context-overflow-code`（32/32 打满）前后对照：

| 观测项 | 二轮 | 三轮 |
| --- | --- | --- |
| `unified_exec` 次数 | **0** | **4** |
| 其中编译/测试命令 | 0 | 4（`cargo test --test repo_feat_context_overflow`、`cargo test --lib agent_loop::error_codes`、一次参数写错的 `cargo test --lib model_client:: key_check::`、`cargo test --lib model_client::`） |
| 档案最后三条 | `message:assistant`「改动完成。现在跑判据测试和受控码表测试。」→ 直接 `turn_end`（调用被吞） | `function_call:unified_exec` → `function_call_output` → `turn_end` |
| FunctionCall / FunctionCallOutput | 41 / 41（落单调用在写档时被剔除） | **45 / 45，落单 0** |

- 三轮的 `cargo test --test repo_feat_context_overflow` 出现在第 23 条 assistant 消息之后
  （纯工具轮不写 assistant 消息，因此实际轮次 ≥23），远早于 32 轮上限，且**是真编译真跑**：
  `3 passed; 0 failed`；同一轮段内 `agent_loop::error_codes` 3 passed、`model_client::` 41 passed
  （中间一次 `cargo test --lib model_client:: key_check::` 是参数写错，`exit code: 1`，一次即纠）。
  该题判据通过、改动 3 个文件。
- 全部 10 题逐题配对检查（按 `call_id`）：**0 个落单调用、0 个重复输出、0 个「输出先于调用」**。
  4 题打满（24/24、32/32、24/24、24/24）的最后一轮都是「工具调用 + 输出」成对落盘后才收口：
  context-overflow 与 apply-patch 的最后一轮是定向测试，title-cap 是 `git status`，
  now-ms-exit 是全量 `cargo test`。
- 代价也如实记录：now-ms-exit 的最后一轮全量 `cargo test` 真的执行了（编译约 24s、41 个沙箱用例红），
  并注入一条「自动修复提醒（第 2/2 次）」；预算随即耗尽，模型没机会回应这条提醒。
  这是「先执行完批次」的正确行为，但也说明打满时最后一次重命令会实打实花掉收尾预算。
- 因此本轮 `BudgetExhausted` 的含义是「预算用完但本轮动作已执行完」，不再是上一轮那种
  「模型说了要跑、命令没跑、历史里只有意图」。

### 专项三：收工验证闸门 —— 0 次否决，因此对通过率影响为 0

- 0 题出现 `VERIFY_FAILED`，0 题出现「宿主验证未通过（写后闸门）」的系统提醒注入
  （全会话的系统注入只有既有的「自动修复提醒（第 N/2 次）」，共 9 条，二轮是 7 条，属自愈闭环，不是收口闸门）。
- 4 题打满 + 4 题 `Completed` = 8 题有源码写入；这 8 题没有任何一题在收口时被判失败，
  也没有「回合被判失败 + 历史写明验证失败原因」的组合出现。
- **可观测性缺口（本轮新增登记）**：评测档案只写 `response_item` 与 `turn_end`，
  `VerificationResult` 事件不进档案，因此无法从档案逐题证明「闸门跑没跑、跑了哪条命令」。
  本轮能确证的是结果面：没有否决、没有失败收口；不能确证过程面。要回答「闸门是否每次执行」，
  需要让评测器把 `VerificationResult` 记进档案或单独的事件流。
- 顺带说明：评测里闸门是默认启用的（`verify: Default::default()` → `enabled: true`、`mode=enforce`）；
  `verify_passes` 的「终端通过计入优先」要求模型原样跑过同一条命令，而本轮模型跑的是
  `cargo test ...` / `cargo clippy ...`，从没跑过就近探测出的 `cargo check --all-targets`，
  因此按代码口径闸门只能执行宿主命令并通过。这是代码推演，同样受限于上面的可观测性缺口。

## 失败分层归因

本轮没有题目失败，也没有回合被判失败，因此这一节回答「为什么打满的题从 1 涨到 4、均值涨了 1.2」。

### 集中在验证策略，不是三件修复

- `title-cap`（17→24）与 `now-ms-exit`（18→24）都在中后段跑了**全量 `cargo test`**。
  该命令在评测沙箱里必然红：41 个失败全部落在 `sandbox::*`、`tools::terminal`、`tools::unified_exec`，
  报错是 AppContainer `0x80070005`、`CreateRestrictedToken 参数错误 0x80070057`、DACL 写拒绝——
  与题目无关。随后自愈闭环注入的「自动修复提醒」把模型指向 `sandbox/acl.rs`、`sandbox/appcontainer.rs`，
  形成一段无效绕行（title-cap 本轮收到 1 条、now-ms-exit 收到 3 条，都是这个形状）。
- `apply-patch-read-guard`（23→24）多出的 1 轮用在分页命令上：`more +0` 可用，`tail -40` 在 cmd 下不存在
  （`[exit code: 255]`），与二轮 `rollout-damaged` 踩的是同一处环境缺口。
- `context-overflow` 的 32 轮没有变多，但构成变了：测试第一次出现前已有 23 条 assistant 消息
  （读与补丁为主），之后有 4 次真实验证，属于上一轮「0 次验证」的直接修复。
- 其余 5 题在 ±2 轮内波动，无工具失败挡住路径。

### 与三件修复的关系

- 三件修复里只有「预算耗尽先执行完批次」会在打满题上多花**执行**时间，不增加轮次（轮次仍被上限卡住）。
- 「断流判失败」与「收口闸门」本轮触发 0 次，不可能贡献轮次上涨。
- 因此轮次上涨不能归因给这批修复；证据是同一批档案里没有任何 `failed` 收口、没有闸门提醒、
  没有任何一次请求错误。

## 这批修复在评测上的净效果

判断：**正确性/可解释性上是净正，通过率无损，效率指标本轮不升反降但不归因于这批修复。**

1. **安全网被证实生效**：预算耗尽时最后一次工具调用成对落盘（上轮被吞的那类），本轮的 4 道打满题
   全部满足；断流判失败与收口闸门没有误伤任何一题。
2. **通过率没有变化**：二轮起就是 10/10，本集对「通过/不通过」已经没有分辨力；
   本轮新增的信息量在过程面（验证是否真的跑了、调用是否成对），不在通过率。
3. **效率指标变差**：轮次均值 15.90→17.10、合计 159→171、打满 1→4、墙钟 +8.9%。
   但增量集中在「模型自己选了全量验证」的 3 题，且与评测环境的沙箱用例必红叠加；
   没有一条证据指向三件修复。10 题 × 1 轮，单题翻转就是 10pp，只能做描述统计。
4. **仍然不能说的话**：不能说「收紧后模型更稳」——本轮没有任何一次收紧被触发；
   也不能说「批次执行让模型更爱验证」——context-overflow 的验证行为变化是模型自己选的，
   样本量不支持因果。

## 评测自身的问题（本轮只登记，未修改评测器）

1. **`VerificationResult` 不进档案**（本轮新增）：收口闸门的执行过程不可审计，只能看结果面。
   建议评测器在 rollout 里补一条 `verification` 记录，或在 child 日志里打点命令与四态。
2. **全量 `cargo test` 在评测沙箱里必红**（本轮新登记，影响最大）：`sandbox::*` 等 41 个用例
   依赖真实受限令牌/ACL，在本工作区跑不起来，还会通过自愈提醒把模型引向无关文件。
   要么在题面/系统提示里点名「本工作区全量 `cargo test` 含已知沙箱红」，要么给白名单验证命令。
3. **判据与预热的 target 目录仍不一致**（一轮起沿用，未修）：首题判据 83.6s，其余多在 32–72s
   （文档题 1.2s）。
4. **每题 robocopy 全量快照**：7613 个文件，setup 合计 552.1s（占墙钟 19.6%）。
5. **cmd 环境能力缺口未在题面说明**：`tail`、`more` 分页两轮都出现；本轮 `apply-patch` 因此多花 1 轮。
6. **打断计数口径仍是 `allow_once`**：本轮 29 次，逐题分布差异大（now-ms-exit 11 次、context-overflow 0 次），
   解读必须看逐题值，不能只看合计。
7. **`repo-doc-max-turns-drift` 判据仍用 `max_turns: N,` 正则抽代码默认值**（一轮起沿用，未修）：
   基座固定 `0bee58e` 时正确，换基座前必须改成定位 `Default` 实现。
